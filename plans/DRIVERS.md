# Драйверная подсистема — архитектура и план реализации

> Общий порядок работ — в `ROADMAP.md` (драйверная модель — M5, диски — M6, сеть — M7, ACPI AML и железо — M9, ввод/USB/звук — M10, Linux-compat — M11, GPU — M12, NDIS — M14). При расхождении прав ROADMAP. Ядро гибридное: блочные и сетевые драйверы живут в юзерспейсе, но VFS, ФС и TCP/IP — в ядре; классы `block` и `net` отдают данные ядру через IPC и разделяемые кольца.

Документ для агента (Claude Code). Описывает **как устроена драйверная модель этой ОС** и **в каком порядке её строить**. Читать целиком перед работой над любым кодом в `drivers/`, `kernel/io/`, `kernel/pci/`, `compat/`.

## 0. Контекст и ограничения

ОС пишется с нуля. Целевая платформа первой фазы: **x86-64, UEFI, QEMU**. Реальное железо — после того как всё работает в эмуляторе.

Цели драйверной подсистемы, в порядке приоритета:

1. Система грузится и работает на типовой машине (диск, клавиатура, экран, сеть).
2. Драйвер не роняет ядро при падении.
3. Широкий охват железа, включая старое.
4. Ограниченная совместимость с драйверами Windows — **только как опциональная поздняя фаза**, см. §8.

ОС предполагает выбор **профиля при установке**: игры / ИИ и разработка / обычная работа / сервер. На драйверную подсистему это влияет слабо — профиль меняет политику и набор запускаемых драйверов, а не их код. Подробно: §6. Порядок реализации профилей задан там же и является обязательным.

### Чего НЕ делаем (явные отказы)

Это решённые вопросы, не переоткрывать:

- **Нет полной бинарной совместимости с драйверами Windows.** Требует реализации всего NT kernel ABI, HAL, PnP/power state machine, реестра, WDF, и всех port/miniport-фреймворков. ReactOS делает это с 1998 года и не закончил. Допустима только узкая совместимость одного класса, §7.
- **Нет поддержки WDDM / GPU-драйверов Windows.** Требует `dxgkrnl`, DirectX-стека, планировщика GPU, модели видеопамяти. Не сделал никто. Графика — свой код поверх GOP/VESA/virtio-gpu.
- **Нет драйверов в ядре** (кроме исключений в §2.4). Модель — юзерспейс.
- **Нет нестабильного внутреннего ABI** по образцу Linux. У нас нет mainline-модели, в которой это оправдано.
- **Не используются утёкшие исходники Microsoft, декомпиляция их бинарников и любой код неясного происхождения.** Только публичная документация и собственные реализации. Это не стилистическое пожелание.

## 1. Принцип: драйверы живут в юзерспейсе

Каждый драйвер — отдельный процесс с собственным адресным пространством. Ядро даёт ему ровно четыре вещи: доступ к MMIO, доставку прерываний, DMA-буферы и IPC-канал.

**Почему так:**

- падение драйвера = падение процесса, не паника ядра; возможен перезапуск;
- отладка обычным отладчиком, без kernel-debug стенда;
- IOMMU ограничивает DMA драйвера его собственными буферами — кривой или враждебный драйвер не перепишет ядро;
- ABI между ядром и драйвером мал, а значит его реально держать стабильным.

**Цена:** IPC и переключение контекста на каждом обмене. Для USB-мыши, принтера, звука — несущественно. Для 100G-сети или NVMe-массива — критично; это закрывается §2.4.

**Следствие для latency ввода (важно, см. цели проекта по GUI):** путь «прерывание → драйвер → compositor → приложение» не должен содержать больше одного переключения контекста на звено. Проектировать его отдельно, с измерением, а не «как получится». Shared-memory ring buffer между драйвером ввода и compositor'ом, без копирования, без сериализации.

## 2. Интерфейс ядро ↔ драйвер

Это и есть **стабильный ABI**. Менять только с версионированием. Держать минимальным — всё, что сюда попало, придётся поддерживать вечно.

### 2.1. Примитивы

```
// Ресурсы устройства
handle_t  dev_open(device_id_t id);
void*     dev_map_bar(handle_t dev, int bar_index, size_t* out_size);
int       dev_read_config(handle_t dev, uint32_t offset, void* buf, size_t len);
int       dev_write_config(handle_t dev, uint32_t offset, const void* buf, size_t len);

// Прерывания: ядро превращает IRQ в сообщение в порт.
// Драйвер блокируется на порту; никакого кода драйвера в контексте прерывания.
handle_t  dev_irq_port(handle_t dev, int vector_index);
int       port_wait(handle_t port, irq_event_t* out, timeout_t t);

// DMA: буфер с гарантированной физической непрерывностью или scatter-gather,
// замапленный в IOMMU строго на этот домен.
dma_buf_t dma_alloc(handle_t dev, size_t len, dma_flags_t flags);
uint64_t  dma_device_addr(dma_buf_t b);   // адрес, видимый устройству
void*     dma_host_addr(dma_buf_t b);     // адрес, видимый драйверу
void      dma_sync(dma_buf_t b, dma_dir_t dir, size_t off, size_t len);
```

Требования:

- `dev_map_bar` возвращает uncached-маппинг; порядок обращений к MMIO обеспечивается явными барьерами в драйвере, не магией ядра.
- Прерывания — **только через порт**. Драйверу никогда не передаётся управление в контексте обработчика. MSI/MSI-X предпочтительны, legacy INTx поддерживается как fallback с разделяемой линией.
- `dma_alloc` без активного IOMMU разрешён только при явном флаге в конфиге ядра; на проде IOMMU обязателен.

### 2.2. Регистрация в подсистеме

Драйвер, инициализировавшись, объявляет себя классом и получает канал от соответствующего менеджера. Классы первой фазы: `block`, `net`, `input`, `display`, `audio`, `bus`.

```
int cls_register(class_t cls, const cls_ops_t* ops, void* ctx);
```

`cls_ops_t` — свой для каждого класса. Он тоже часть стабильного ABI.

### 2.3. Матчинг и загрузка

Шинный драйвер (PCI, USB) перечисляет устройства и публикует их в дереве устройств. Менеджер устройств подбирает драйвер по манифесту.

Манифест — TOML рядом с бинарником драйвера:

```toml
name = "ahci"
class = "block"
[[match]]
bus = "pci"
class_code = 0x010601        # Mass storage / SATA / AHCI 1.0
[[match]]
bus = "pci"
vendor = 0x8086
device = [0x2922, 0x2829]
score = 100                  # при нескольких совпадениях выигрывает больший
```

Матчинг по сигнатуре класса предпочтительнее матчинга по vendor/device: один драйвер накрывает весь парк устройств, соответствующих спецификации. Vendor/device — для обхода errata конкретных чипов.

### 2.4. Единственное исключение: in-kernel fast path

Драйвер может быть собран в ядро **только** если выполнены все условия:

- измерено, что IPC-накладные расходы доминируют в профиле;
- драйвер прошёл ревью;
- есть юзерспейсный вариант того же драйвера как fallback.

Кандидаты в будущем: NVMe, 10G+ сеть. **На старте — ни одного.** Не начинать с оптимизации.

## 3. Harness — делается ПЕРВЫМ, до кода ядра

Без автоматического цикла «собрал → запустил → увидел результат» разработка драйверов вслепую невозможна. Это не инфраструктурная мелочь, это главный инструмент.

Нужно в `tools/`:

1. **`run.sh`** — запуск QEMU с полным набором диагностики:
   - `-serial stdio` — весь лог ядра в stdout, с самого раннего этапа загрузки;
   - `-d int,guest_errors -D qemu.log` — трассировка прерываний и исключений;
   - `-s -S` опционально — gdb-стаб на :1234;
   - `-no-reboot -no-shutdown` — чтобы тройная ошибка не превращалась в бесконечный ребут, а оставляла состояние.
2. **Ранний serial-вывод в ядре.** Первое, что инициализируется, — COM1 на 0x3F8. До инициализации памяти, до всего. Макрос `early_print` обязан работать на третьей инструкции ядра.
3. **`test.sh`** — прогон в QEMU, сравнение serial-вывода с ожидаемым, exit code. Это то, по чему агент понимает «работает / не работает».
4. **Протокол выхода:** ядро пишет в порт `0xf4` (`-device isa-debug-exit`) код результата. Тест становится однозначным.
5. **Набор QEMU-конфигураций** под каждый класс устройств: `-device ahci`, `-device nvme`, `-device e1000`, `-device qemu-xhci`, `-device virtio-gpu-pci`, `-device intel-hda`. Каждый драйвер разрабатывается против своей конфигурации.

**Правило для агента: ни один драйвер не считается написанным, пока `test.sh` с его конфигурацией не проходит.** Код, который «выглядит правильно», но не прогнан, — не сделан.

## 4. Фаза 1 — class drivers (основной объём работы)

Ключевая мысль: **широкий охват железа даётся не количеством драйверов, а стандартизированными классами.** Тремя десятками драйверов по открытым спецификациям накрывается большая часть реальных машин, включая старые.

Порядок реализации — строго такой, каждый следующий опирается на предыдущие.

### 4.1. Фундамент
| Драйвер | Спецификация | Зачем |
|---|---|---|
| PCI/PCIe bus | PCI Local Bus Spec, PCIe Base Spec | перечисление устройств, BAR'ы, MSI/MSI-X, config space через ECAM |
| ACPI (минимум) | ACPI Spec | таблицы MADT (APIC), MCFG (ECAM), FADT; интерпретатор AML — позже |
| APIC / IOAPIC | Intel SDM vol.3 | маршрутизация прерываний |
| HPET / TSC | — | таймеры |

### 4.2. Вывод и ввод — чтобы вообще что-то увидеть
| Драйвер | Спецификация |
|---|---|
| UEFI GOP framebuffer | UEFI Spec | 
| VESA/VBE | VBE 3.0 — для legacy-загрузки |
| PS/2 keyboard + mouse | 8042 controller |
| virtio-gpu | VIRTIO Spec v1.2 |

### 4.3. Диски
| Драйвер | Спецификация |
|---|---|
| AHCI | AHCI 1.3.1 (Intel, открытый документ) |
| NVMe | NVM Express Base Spec |
| IDE/ATA PIO | ATA/ATAPI-6 — для очень старых машин |
| virtio-blk | VIRTIO Spec |

### 4.4. USB — даёт огромный охват периферии
| Драйвер | Спецификация |
|---|---|
| xHCI | eXtensible Host Controller Interface Spec |
| EHCI / OHCI / UHCI | соответствующие спеки — старые машины |
| USB HID class | USB HID Spec — все клавиатуры, мыши, геймпады разом |
| USB Mass Storage (BOT) | USB MSC Spec — все флешки разом |
| USB CDC | — сетевые адаптеры |

USB-классы — лучшее соотношение «строк кода к поддержанным устройствам» во всём проекте. Один драйвер HID закрывает тысячи моделей.

### 4.5. Сеть
| Драйвер | Примечание |
|---|---|
| e1000 / e1000e | открытая документация Intel, работает в QEMU по умолчанию |
| RTL8139 / RTL8169 | огромный парк дешёвых карт |
| virtio-net | — |

### 4.6. Звук
| Драйвер | Примечание |
|---|---|
| Intel HDA | один контроллер — почти весь парк звуковых устройств с 2004 года |

**Критерий завершения фазы 1:** система грузится с AHCI-диска на реальном железе, работает клавиатура, есть изображение, пингуется сеть. Разбит в ROADMAP: диск и сеть на железе — M9 (серверный профиль), экран и ввод — M10. Таблицы 4.2 и 4.6 не начинать до M10 (§9.2).

## 5. Фаза 2 — слой совместимости с драйверами Linux

Это **ответ на задачу «много драйверов для старого железа»**. В mainline-дереве Linux несколько десятков тысяч драйверов, покрывающих практически всё когда-либо выпущенное оборудование, и они открыты.

Нужна не бинарная совместимость, а **исходная**: реализовать подмножество Linux kernel API, чтобы драйверы из mainline собирались против нашего ядра.

### Прецеденты, которые стоит изучить перед началом

- **Haiku** — слой совместимости с сетевыми драйверами FreeBSD, работает в продакшене;
- **Genode DDE** (Device Driver Environment) — запуск линуксовых драйверов в изоляции;
- **NetBSD rump kernels** — драйверы ядра как юзерспейсные библиотеки;
- **LKL** (Linux Kernel Library) — ядро Linux собранное библиотекой под чужой хост.

Это не теория, это реализованные подходы. Начинать с чтения их исходников, а не с чистого листа.

### Что реализуется в слое

```
compat/linux/
  mm.c        kmalloc, kfree, vmalloc, страничные аллокаторы, GFP-флаги
  irq.c       request_irq / free_irq поверх наших портов прерываний
  io.c        ioremap, readl/writel, inb/outb
  dma.c       dma_alloc_coherent, dma_map_single, scatterlist
  sync.c      spinlock_t, mutex, completion, wait_queue
  work.c      workqueue, tasklet, timer_list
  pci.c       pci_register_driver, probe/remove, pci_iomap
  device.c    struct device, struct device_driver, bus_type, match
  net/        netdev, sk_buff, NAPI
  usb/        usb_driver, urb
```

Драйвер исполняется в отдельном процессе, как и наши нативные; слой совместимости — библиотека, слинкованная с ним.

### Порядок

1. Начать с **одного** драйвера простой PCI-сетевой карты, доступной в QEMU.
2. Реализовать ровно те функции, которых не хватает для сборки и работы именно его.
3. Добавлять драйверы по одному, расширяя слой по фактической потребности.

Не пытаться реализовать «весь Linux API» заранее — это несколько миллионов строк, и 95% не понадобится.

### Юридическое

Ядро Linux — GPLv2. Слой совместимости, линкуемый с кодом драйверов, с высокой вероятностью является производной работой со всеми вытекающими обязательствами. **Решить этот вопрос до написания первой строки `compat/linux/`,** а не после. Изоляция драйверов в отдельные процессы с IPC-границей — аргумент в пользу разделения, но не гарантия. Если проект планируется закрытым — этот путь, вероятно, закрыт целиком.

## 6. Профили установки

При установке выбирается один из четырёх профилей. **Драйверный стек при этом один и тот же** — профиль определяет политику и состав запускаемых драйверов, а не отдельные ветки кода. Никаких `#ifdef PROFILE_GAMING` в драйверах быть не должно.

### 6.1. Что профиль реально меняет

| Профиль | Политика планировщика | Память | Драйверы | Прочее |
|---|---|---|---|---|
| Игры | latency-first, короткий тик, высокий приоритет потокам ввода и GPU-submit | huge pages, агрессивный префетч | полный набор | минимум фоновых служб |
| ИИ / разработка | throughput-first, длинные кванты | huge pages, pinned-память под DMA, NUMA-локальность | полный набор + приоритет GPU compute | — |
| Работа | баланс, отзывчивость GUI | обычная | полный набор | энергосбережение активно |
| Сервер | throughput, честность между задачами | обычная | **без display / audio / input** | headless, без compositor'а |

Механизм: менеджер устройств читает профиль и решает, какие манифесты активировать и с какими параметрами. Расширение §2.3, не новая подсистема.

### 6.2. Матрица «профиль → обязательные драйверы»

| | Сервер | Работа | ИИ | Игры |
|---|---|---|---|---|
| PCI, ACPI, APIC, таймеры | ✅ | ✅ | ✅ | ✅ |
| AHCI / NVMe | ✅ | ✅ | ✅ | ✅ |
| e1000 / RTL / virtio-net | ✅ | ✅ | ✅ | ✅ |
| xHCI + USB HID / MSC | — | ✅ | ✅ | ✅ |
| Framebuffer (GOP/VESA) | — | ✅ | ✅ | ✅ |
| PS/2 ввод | — | ✅ | ✅ | ✅ |
| Intel HDA | — | ✅ | — | ✅ |
| GPU с 3D | — | — | ✅ | ✅ |

Правый столбец требует всего левого. **Поэтому порядок реализации профилей — справа налево по сложности: сервер → работа → ИИ → игры.**

### 6.3. Достижимость профилей — честная оценка

Это не пессимизм, а план. Архитектуру нельзя строить под цель, которая недостижима по причинам вне драйверов.

**Сервер — достижим.** Узкий набор железа, headless, прикладной софт открыт и собирается из исходников. Единственный профиль, доводимый до состояния «работает по-настоящему» силами одного человека. Он же полностью валидирует PCI, прерывания, DMA, блочный и сетевой стек. **Делать первым.**

**Работа — упирается не в драйверы, а в браузер.** Порт Chromium/Firefox требует огромной поверхности POSIX, графики, шрифтов, ввода, аудио, видеоускорения — крупнейшая задача любой молодой ОС (Haiku и ReactOS бьются над этим годами). Промежуточная цель: собственные приложения и софт, собираемый из исходников.

**ИИ — упирается в CUDA.** Проприетарный стек NVIDIA недоступен без сотрудничества с NVIDIA; PyTorch и практически всё обучение завязаны на него. Реалистично: **инференс через Vulkan compute** (образец — Vulkan-бэкенд `llama.cpp`). Обучение — вне досягаемости. Фиксируем это как границу профиля, а не как временное ограничение.

**Игры — самый тяжёлый профиль.** Нужны одновременно: свой 3D-драйвер с Vulkan, трансляция Direct3D поверх него (класса DXVK / vkd3d-proton), слой Win32 уровня Wine. Отдельная стена — **античиты**: EAC, BattlEye, Vanguard работают в ядре и требуют доверенной подписанной среды; они не включаются даже для Linux без явного решения издателя игры. **Мультиплеер с античитом не заработает при любом объёме вложенной работы — не проектировать под него ничего.** Реалистичная цель — одиночные игры через трансляцию D3D→Vulkan.

Для калибровки ожиданий: Valve шла к играбельности SteamOS более десяти лет, большой командой, финансируя Proton, Mesa и DXVK — и это поверх готового Linux со всеми его драйверами.

## 7. GPU

Полноценный GPU-драйвер (modeset, управление видеопамятью, командные буферы, 3D) — задача масштаба всей остальной ОС. Но она не бинарная: есть лестница, по которой можно подниматься, получая полезный результат на каждой ступени.

### 7.1. Лестница

1. **UEFI GOP / VESA linear framebuffer** — изображение есть, система пригодна для работы и установки.
2. **`virtio-gpu`** — в виртуалке; с virgl/venus доступно и 3D-ускорение.
3. **Программный compositor с SIMD** — для GUI этого достаточно, особенно когда приоритет отдан latency ввода, а не 3D.
4. **Нативный Intel iGPU** по открытым PRM (Intel публикует документацию на свои GPU). Референс — `i915` в Linux и Mesa `iris`. Наиболее документированная платформа, единственный разумный путь к собственному Vulkan-драйверу.
5. **Или: DRM-драйверы Linux через расширенный слой §5.**

### 7.2. Про путь через Linux DRM

Это **рабочий прецедент, а не теория**: FreeBSD через `linuxkpi` и порт `drm-kmod` запускает настоящие линуксовые `i915` и `amdgpu` — с ускорением, Mesa и работающим десктопом.

Цена выше, чем для сетевого драйвера: DRM тянет DMA-buf, GEM/TTM (менеджер видеопамяти), `drm_sched`, fences, shmem, модель KMS. Это существенное расширение §5. Но путь существует и проверен — в отличие от §7.3.

Оценивать эту ветку только после того, как §5 работает на сетевых драйверах.

### 7.3. Почему драйверы GPU от Windows (WDDM) исключены

Решение окончательное, вопрос закрыт. Обоснование — чтобы к нему не возвращаться:

WDDM-драйвер состоит из **двух половин в разных местах**:

- **KMD** (`nvlddmkm.sys` и аналоги) — в ядре, но не самостоятелен: подключается к `dxgkrnl.sys` через интерфейс из сотни с лишним DDI (`DxgkDdiCreateAllocation`, `DxgkDdiSubmitCommand`, `DxgkDdiPatch`, `DxgkDdiBuildPagingBuffer`, …);
- **UMD** (`nvwgf2umx.dll` и аналоги) — живёт **в адресном пространстве каждого приложения**, загружается рантаймом Direct3D, реализует D3D DDI и компилирует шейдеры из DXBC/DXIL в ISA конкретного GPU.

Значит, чтобы драйвер вообще запустился, нужен не только ядерный слой, но и **рантайм D3D11/D3D12 плюс DXGI** — иначе UMD некому загрузить и вызвать.

Сам `dxgkrnl` — это **VidMm** (GPU-виртуальные адресные пространства, пейджинг аллокаций между VRAM и системной памятью, вытеснение, патчинг командных буферов), **VidSch** (планировщик GPU: очереди, приоритеты, preemption, TDR), **VidPn** (топология вывода, мониторы, modeset) и синхронизация (fences, monitored fences, межпроцессные ресурсы). Плюс версионирование WDDM 2.0 / 2.7 / 3.0 / 3.1 с разными обязательными DDI. И всё это — поверх полной реализации NT-ядра из §8.

Объём сопоставим со всей остальной ОС при нулевом прецеденте успеха: к этому не подступался никто, включая ReactOS.

### 7.4. Если цель — «чтобы шли игры под Windows»

Тогда WDDM не нужен и был бы ошибкой направления. Правильный подход **противоположный**: не запускать виндовый драйвер, а реализовать виндовый **API** поверх собственного GPU-стека — как делают Wine, DXVK и vkd3d-proton, транслируя Direct3D 9/11/12 в Vulkan (часто быстрее, чем на самой Windows). Это работа уровня прикладного слоя, и она требует, чтобы внизу уже был свой драйвер с Vulkan.

Nvidia и AMD с нуля — не планировать ни при каком раскладе.

## 8. Фаза 3 (опциональная) — узкая совместимость с драйверами Windows

**Открывать эту фазу только после того, как фазы 1 и 2 полностью закрыты.** Это надстройка, а не фундамент.

### Реалистичная постановка

Полная совместимость невозможна (см. §0). Возможна совместимость **одного класса драйверов с ограниченной поверхностью API** — ровно так, как это делал `ndiswrapper` в Linux и Project Evil во FreeBSD. Оба работали. Оба ограничивались NDIS-сетевыми драйверами. Оба в итоге были выпилены, когда нативные драйверы догнали по охвату.

### Что потребуется даже для узкого случая

1. **PE/COFF загрузчик** для `.sys`: секции, релокации, разрешение импортов. Самая простая часть, 1–2 дня.
2. **Соглашение о вызовах**: Microsoft x64 ABI (RCX, RDX, R8, R9, 32 байта shadow space, другой набор callee-saved регистров) против System V. Нужны трамплины в обе стороны. Либо компилировать слой с `__attribute__((ms_abi))`.
3. **Подмножество экспортов `ntoskrnl`**, достаточное для NDIS-miniport: `IoAllocateMdl`, `MmGetSystemAddressForMdlSafe`, `KeInitializeSpinLock`, `KeAcquireSpinLock`, `ExAllocatePoolWithTag`, `KeSetEvent`, `IoConnectInterrupt` и т.д. — десятки, не тысячи, но каждая с точной семантикой.
4. **Эмуляция IRQL**: как минимум PASSIVE_LEVEL / DISPATCH_LEVEL, с корректным запретом вытеснения и запретом обращения к страничной памяти на DISPATCH.
5. **Реализация NDIS miniport API**: `NdisMRegisterMiniport`, `NdisMAllocateSharedMemory`, `NdisMIndicateReceiveNetBufferLists`, обработка OID-запросов.
6. **Минимальный реестр**, потому что драйвер читает оттуда параметры, и **парсер INF** для их извлечения.

### Подводные камни, которые съедают время

- Структуры NT имеют версии; драйвер, собранный под Windows 10, ожидает одного layout'а, под Windows 7 — другого. Фиксировать одну целевую версию.
- KMDF-драйверы **не вызывают WDM напрямую** — они линкуются к `Wdf01000.sys`. Распространять этот файл нельзя. Значит нужна собственная реализация KMDF поверх собственной реализации WDM. Это удваивает объём. **Ограничиться чистыми WDM/NDIS-драйверами.**
- Ошибка в layout структуры не проявляется как ошибка компиляции. Она проявляется как повреждение памяти. Каждая структура, передаваемая драйверу, должна иметь unit-тест на `offsetof` всех полей и `sizeof`.

### Критерий отказа

Если на реализацию узкого NDIS-случая ушло больше ~3 месяцев без работающего драйвера реальной карты — закрывать фазу. Охват, который она даёт, не стоит бесконечных вложений; те же устройства почти наверняка уже поддержаны через §5.

## 9. Правила работы для агента

1. **Harness первым.** До кода ядра. См. §3.
2. **Серверный профиль — первая цель.** Не браться за GPU, звук и ввод, пока не работает связка «грузимся с диска + сеть». См. §6.2.
3. **Один драйвер — одна задача.** Не писать три драйвера параллельно.
4. **Спецификация перед кодом.** Для каждого драйвера — найти и прочитать официальный документ (AHCI 1.3.1, xHCI, NVMe Base, VIRTIO). Не реконструировать регистры по чужому коду и не угадывать по памяти. Если спека не найдена — остановиться и сказать об этом, а не писать правдоподобный код.
5. **Никакой оптимизации до измерения.** Никаких in-kernel драйверов, zero-copy и lock-free на старте.
6. **Ничего не считается готовым без прогона в QEMU.** `test.sh` зелёный — или не сделано.
7. **Каждая структура, разделяемая с устройством или чужим ABI**, сопровождается статическими проверками размера и смещений полей (`static_assert(offsetof(...) == ...)`).
8. **Барьеры памяти — явно.** При работе с MMIO и DMA-кольцами не полагаться на порядок, который «и так должен быть».
9. **Стабильный ABI (§2) не меняется молча.** Любое изменение — отдельное обсуждение и версия.
10. **Профиль — это политика, не ветка кода.** Никаких `#ifdef` по профилю в драйверах.
11. **Чистота происхождения кода.** Только публичные спецификации и собственные реализации. Никаких утёкших исходников, никакой декомпиляции чужих бинарников.
12. **При неопределённости — спросить, а не угадать.** Неверная догадка в драйверной работе не ловится компилятором и обнаруживается через недели.

## 10. Краткая сводка решений

| Вопрос | Решение | Обоснование |
|---|---|---|
| Где исполняются драйверы | юзерспейс | изоляция, отладка, перезапуск |
| Стабильность ABI | стабильный, версионированный | нет mainline-модели, оправдывающей обратное |
| Изоляция DMA | IOMMU обязателен | драйвер не должен иметь доступа ко всей памяти |
| Доставка прерываний | сообщение в порт, MSI-X | нет кода драйвера в контексте прерывания |
| Матчинг | манифест TOML, приоритет class-матчинга | один драйвер на весь класс устройств |
| Охват старого железа | class drivers + Linux-compat | открытые спеки и открытые драйверы |
| Совместимость с Windows | узкий NDIS-случай, опционально, последней | полная — арифметически невозможна |
| GPU | лестница: framebuffer → virtio-gpu → Intel iGPU или Linux DRM | WDDM требует dxgkrnl + рантайм D3D; прецедентов нет |
| Игры под Windows | трансляция D3D→Vulkan поверх своего драйвера | путь Wine/DXVK, а не загрузка чужого драйвера |
| Профили установки | политика + состав драйверов, единый стек | нет смысла в четырёх системах |
| Порядок профилей | сервер → работа → ИИ → игры | слева направо растёт зависимость от GPU и прикладного слоя |
