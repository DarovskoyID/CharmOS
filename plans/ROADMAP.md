# CharmOS — единая лестница фаз

**Главный документ по порядку работ.** Если он расходится с `DRIVERS.md` или
`os-gui-design.md`, прав этот документ. Те два — справочники по своим
подсистемам: что и почему. Здесь — в каком порядке и когда работа считается
готовой.

Решения, на которых построен план, — в журнале решений `os-gui-design.md`.
Кратко: реальная система, x86-64 (платформенный код только в `arch/`),
сначала QEMU, freestanding C++23, капабилити, гибридное ядро (ФС и TCP/IP в
ядре, драйверы в юзерспейсе), стабильный ABI, свой UEFI-загрузчик, весь код
свой (исключения — фазы M11 и M14), WSL2 + CMake/Ninja.

## Правила лестницы

1. **Не начинать фазу N+1, пока у фазы N не зелёные все тесты из «Готово
   когда».** Тесты — автоматические (`tools/test.sh <фаза>`), а не «на глаз».
2. **Сначала интерфейс, потом код.** ABI стабилен с первого дня, поэтому каждый
   интерфейс, который пересекает границу (boot→kernel, syscall, ядро↔драйвер,
   классы драйверов), сначала описывается в `docs/abi/`, проходит обсуждение и
   только потом реализуется. Изменение после фиксации — только новой версией.
3. **Спека перед драйвером.** PDF кладётся в `docs/specs/` до начала работы
   (DRIVERS.md §9.4).
4. Код фазы, которая ещё не наступила, не пишется. Агент сообщает об этом и
   останавливается.

## Блок A. Фундамент (только QEMU)

### M0. Окружение и harness
WSL2 (Ubuntu), clang/lld, QEMU (OVMF), gdb. CMake + Ninja, toolchain-файлы для
целей: `uefi` (PE32+), `kernel` (ELF x86-64, без red zone, mcmodel=kernel),
`user`, `host` (тесты на хосте). `tools/run.sh`, `tools/test.sh` по DRIVERS.md
§3: serial в stdout, `-d int,guest_errors`, `-no-reboot -no-shutdown`,
`isa-debug-exit`. Сборка ESP-образа. Фреймворк хост-тестов для кода без
железа (аллокаторы, парсеры, структуры данных). CI на GitHub Actions:
сборка + `test.sh` + хост-тесты.

**Готово когда:** заглушка-UEFI-приложение печатает строку в serial,
`test.sh m0` возвращает 0 через `isa-debug-exit`, хост-тест проходит, CI зелёный.

### M1. Свой UEFI-загрузчик
Сначала — `docs/abi/boot.md`: версионированная структура передачи управления
(карта памяти, GOP-фреймбуфер, RSDP, cmdline, модули/initrd, физический адрес
ядра). Загрузчик читает ELF ядра с ESP через UEFI-протоколы, маппит его в
higher half, получает карту памяти, делает `ExitBootServices`, прыгает в ядро.
Ядро не знает ничего о загрузчике, кроме этой структуры.

**Готово когда:** ядро печатает в serial содержимое структуры (карта памяти,
разрешение экрана, адрес RSDP); тест проверяет формат; неверная версия
структуры даёт понятную панику.

### M2. Ядро, минимум
Ранний serial (первым), GDT/TSS, IDT, обработчики исключений с паникой,
бэктрейсом и дампом регистров в serial. Физический аллокатор страниц,
виртуальная память (higher half, свои таблицы страниц), kernel heap
(аллокации возвращают Result). Статические таблицы ACPI без AML: MADT, MCFG,
FADT, HPET. LAPIC, IOAPIC, HPET, калибровка TSC, таймер.

**Готово когда:** тесты на исключения (#PF, #GP, #DE ловятся и печатаются),
стресс-тест аллокаторов, тик таймера с измеренной частотой, хост-тесты
аллокаторов.

**Статус (2026-10-14): закрыт.** Тесты `tests/qemu/m2/*`. Отличия от плана и
отложенное:
- MCFG перенесён в M5: его формат задан PCI Firmware Specification, а не ACPI.
- Проверка invariant TSC (CPUID 80000007H) отложена: нужен SDM Vol. 2A/3B.
- `BootloaderReclaimable` и `AcpiReclaimable` пока не возвращаются в пул фреймов.
- Только xAPIC (MMIO); если прошивка включила x2APIC — паника. x2APIC — в M3 вместе с SMP.
- Стек ядра — стек загрузчика без защитной страницы; свои стеки с guard page — в M3.

### M3. SMP, многозадачность, юзерспейс
Запуск AP, примитивы синхронизации (spinlock, mutex) с правилом порядка
захвата, per-CPU данные. Потоки, переключение контекста, планировщик за чистым
интерфейсом. Ring 3, `syscall`/`sysret`, адресные пространства процессов,
ELF-загрузчик, минимальный рантайм для юзерспейса (crt0 + обёртки syscall).

**Готово когда:** два процесса одновременно на разных CPU делают syscall;
падение процесса не роняет ядро; стресс-тест планировщика на 4 vCPU.

**Статус (2026-10-14): закрыт.** Тесты `tests/qemu/m3/*`. Отличия от плана и
отложенное:
- Syscall ABI v1.0 спроектирован здесь, а не в M4 (журнал решений); хендлы и
  капабилити — по-прежнему M4.
- initrd (docs/abi/initrd.md) появился в M3: программы пользователя грузятся
  из него.
- Потоки не мигрируют между CPU; стеки и структуры завершённых потоков
  переиспользуются, а не освобождаются (нужен TLB shootdown).
- У процесса один поток; только x87/SSE (AVX не включён: нет XSAVE).
- NMI между `swapgs` и `sysret` увидел бы GS пользователя: NMI пока не
  обрабатываются (паника), исправить вместе с обработкой NMI.

### M4. Капабилити, IPC, syscall ABI v1 — ключевая фаза
Сначала — `docs/abi/syscalls.md` и `docs/abi/ipc.md`: таблица хендлов, права,
передача хендлов, каналы, порты, разделяемая память, коды ошибок, версия ABI.
Это ABI, который больше не ломается. Затем реализация.

**Готово когда:** процесс A передаёт B капабилити на страницу, B читает, у C
доступа нет; урезание прав при передаче; отзыв; тест на подделку хендла;
замер IPC round-trip в циклах (база для дальнейшего сравнения).

**Статус (2026-10-14): закрыт.** Тест `tests/qemu/m4/ipc` (cap_a/b/c, chan,
ping/pong), хост-тесты таблицы хендлов. ABI — docs/abi/ipc.md (v1.1).
- Отзыв по дереву происхождения: снимает хендлы в таблицах, в непрочитанных
  сообщениях и отображения VMO (со сбросом TLB на CPU процесса через IPI).
- Замер (QEMU TCG, без KVM, ping и pong на разных CPU): ~155 мкс
  (~550 тыс. тактов TSC) на обмен. Число для сравнения только внутри этой же
  среды; быстрый путь IPC (прямое переключение на получателя) не делался —
  правило 9, сначала замеры на железе.
- Вся синхронизация IPC — одна блокировка (ранг Ipc); дробить — после замера.
- Порты (объект ожидания нескольких источников) — в M5 вместе с прерываниями.

## Блок B. Серверный профиль (QEMU → железо)

### M5. Драйверная модель
По DRIVERS.md §1–2. Сначала — `docs/abi/driver.md`. PCI/PCIe через ECAM в
ядре, MSI/MSI-X, прерывания как сообщения в порт, IOMMU (Intel VT-d, в QEMU
`-device intel-iommu`), DMA API, менеджер устройств, манифесты TOML (свой
парсер), перезапуск упавшего драйвера.

**Готово когда:** тестовый драйвер получает BAR, IRQ и DMA-буфер; DMA за
пределы своего домена ловится IOMMU; убитый драйвер перезапускается
менеджером.

**Статус (2026-10-14): закрыт.** Тесты `tests/qemu/m5/` (pci, drivers, iommu),
хост-тесты манифестов и DMAR. ABI — docs/abi/driver.md (v1.2), `abi_version`
сообщает 1.2.
- Драйвер `edu` (user/drivers/edu) по манифесту: BAR0, MSI через порт, DMA в
  обе стороны через буфер `dma_alloc`; затем пишет мимо домена — VT-d
  фиксирует ошибку, ядро гасит Bus Master, убивает драйвер, менеджер
  перезапускает его (5 раз, потом сдаётся).
- VT-d: legacy-режим (Root/Context), таблицы второго уровня 3 или 4 уровня,
  инвалидация через регистры (без очереди), прерывание ошибок. Поддержан
  некогерентный обход таблиц (QEMU сообщает ECAP.C = 0) — через CLFLUSH.
- Домен — на объект Device (на запуск драйвера). Пока драйвер владеет одним
  устройством, это и есть «домен на процесс-драйвер»; общий домен для
  нескольких устройств одного драйвера — когда появится такой драйвер.
- Убийство чужого процесса — флагом: процесс умирает при выходе из системного
  вызова или по тику таймера в ring 3; заблокированный без срока — когда
  проснётся (его устройство к этому моменту уже погашено).
- Не сделано и не проверено: MSI-X (у edu его нет — сделать с первым
  устройством, где он есть, M6/M7); `iommu=off` реализован, но не покрыт
  тестом (DMA edu 28-битный, физический буфер может оказаться выше 256 МиБ);
  IOVA выдаются без переиспользования (адреса домена не возвращаются до его
  уничтожения); области DMAR с мостами не поддержаны (устройства за ними без
  DMA, с записью в журнал); переназначение прерываний VT-d — нет.

### M6. Диски и файловые системы
Драйверы в порядке: virtio-blk → AHCI → NVMe (юзерспейс). В ядре: блочный
слой (общий с драйвером кольцом через разделяемую память), page cache, VFS.
ФС: FAT32 (ESP), ext2 (корень, чтение и запись). Своя ФС — позже, не в этой
фазе.

**Готово когда:** для каждой из трёх QEMU-конфигураций: монтирование корня,
чтение/запись/fsync файла, переживает перезагрузку; падение блочного драйвера
во время I/O не портит ФС и не роняет ядро.

**Статус (2026-10-14): закрыт.** Тесты `tests/qemu/m6/` (10 сценариев),
хост-тесты GPT/FAT32/ext2 и проверка образов e2fsck и fsck.fat. ABI —
docs/abi/block.md, docs/abi/fs.md, driver.md §9 (v1.3), `abi_version` 1.3.
- Драйверы в юзерспейсе: virtio-blk, NVMe, AHCI; блочное кольцо с
  повтором запросов после падения драйвера; IOMMU для всех.
- Page cache, VFS, монтирование `root=diskNpM` по GPT, ext2 и FAT32 на
  чтение и запись; файловые вызовы 23–30 из ring 3.
- Каждая из трёх конфигураций: монтирование, чтение/запись/fsync, вторая
  загрузка с тем же образом. Образы после работы CharmOS проходят e2fsck и
  fsck.fat. Драйвер NVMe убит во время файлового I/O — запросы повторены,
  ФС цела (m6/nvme3_crash, nvme4_fsck).
- Номера дисков закрепляются при запуске драйверов (в порядке PCI).
- Ограничения: в каждый момент один запрос на диск (правило 9), один диск на
  драйвер (AHCI — первый порт с диском, NVMe — пространство имён 1), нет
  NCQ, нет переименования и ссылок (fs.md §7). Формат H2D FIS и часть
  PxSERR — по вторичной сводке (sata-ahci-summary.md), link/PHY проверены
  только в QEMU. ext2 — по вторичному описанию (Poirier).


### M7. Сеть
Драйверы: virtio-net → e1000/e1000e (RTL8139/8169 перенесены в M9: открытых
даташитов Realtek нет, решение автора 2026-10-14). В ядре — свой TCP/IP:
Ethernet, ARP, IPv4, ICMP, UDP, TCP, DHCP-клиент, DNS-клиент; сокеты как
капабилити. IPv6 — после M9.

**Готово когда:** DHCP получает адрес в QEMU user-net, ping хоста, TCP echo
сервер выдерживает тест с хоста (много соединений, потери пакетов через
`netem` или аналог).

**Статус (2026-10-14): закрыт.** Тесты `tests/qemu/m7/` (net, tcp, sock,
tcp_e1000, udp). ABI — docs/abi/net.md, docs/abi/socket.md (v1.4),
`abi_version` 1.4.
- Драйверы в юзерспейсе: virtio-net (MSI-X) и e1000 (опросом: у 8254x только
  INTx, маршрутизация INTx через `_PRT` — M9).
- В ядре: Ethernet, ARP, IPv4 (без фрагментации), ICMP, UDP, DHCP-клиент,
  DNS-клиент, TCP (RFC 9293; RTO по RFC 6298 с минимумом 200 мс вместо
  «SHOULD» 1 с; медленный старт, избегание перегрузки и быстрая повторная
  передача по RFC 5681; сборка вне порядка; Нейгл).
- Сокеты из ring 3 по хендлу Net с сужаемыми правами; TCP и UDP;
  готовность через порт (опросом раз в 10 мс — правило 9).
- Критерий: эхо-сервер в ring 3 выдерживает 10 параллельных соединений
  с хоста при потере каждого 10-го сегмента; клиент на хосте сверяет эхо.
- Ограничения: один интерфейс, нет IPv6 (после M9), нет SACK, окна до 64 КиБ
  (без масштабирования), фиксированный TIME-WAIT 2 с, DNS — один запрос за
  раз; RTL8139/8169 — в M9. Для e1000 в простое повторяется запись RDT —
  обход поведения модели QEMU (см. комментарий в драйвере).


### M8. Базовый юзерспейс
Своя libc (POSIX-подмножество, растёт по потребности), init и менеджер
служб (он же запускает драйверы), системный журнал, шелл, базовые утилиты,
простой HTTP-сервер как эталонная серверная нагрузка.

**Готово когда:** загрузка до шелла по serial; HTTP-сервер отдаёт файл с
диска на хост; убитая служба перезапускается.

### M8.5. Защищённая системная область и магазин приложений
Решение автора от 2026-10-14 (журнал решений). Закрытая область диска, как
в macOS: в ней программы, установленные из магазина автора; доступа к ней нет
ни у программ, ни у владельца компьютера, ни при физическом доступе к диску.
- **Внутри ОС — капабилити:** хендл каталога закрытой области ядро выдаёт
  только службе установки (и загрузчику программ на чтение). Суперпользователя
  нет, выключить защиту изнутри нельзя. Путь к ней через `..` невозможен
  (docs/abi/fs.md).
- **Подписи:** пакеты магазина подписаны ключом автора (Ed25519 + SHA-256,
  своя реализация); открытый ключ зашит в ОС. Подпись проверяется при
  установке и при каждом запуске — изменённый файл не запустится.
- **Программы не из магазина** ставятся и работают, но только вне закрытой
  области и с меньшими правами.
- Формат пакета, служба установки, клиент магазина (загрузка по HTTP из M7/M8)
  — сначала ABI в `docs/abi/`, согласование, потом код.
- **Физический доступ** (другая ОС, диск в другом компьютере): системный
  раздел шифруется, ключ — в TPM 2.0 и выдаётся только при доверенной
  загрузке (Secure Boot со своим ключом, измерения в PCR). Требует железа —
  эта часть делается в M9 и после; в M8.5 — точки расширения под неё.
- Спецификации, которые понадобятся: RFC 8032 (Ed25519), FIPS 180-4
  (SHA-256), для шифрования диска — NIST SP 800-38E (XTS-AES) и FIPS 197
  (AES), TCG TPM 2.0 Library, UEFI Secure Boot (уже есть UEFI 2.11).

**Готово когда:** пакет, подписанный ключом автора, ставится в закрытую
область и запускается; пакет с испорченной подписью или изменённым файлом
отвергается; обычная программа (и шелл владельца) не может ни открыть, ни
перечислить закрытую область; программа не из магазина ставится вне её.
Шифрование и TPM — критерий M9.

### M9. ACPI AML и выход на реальное железо
Свой AML-интерпретатор (самый рискованный пункт плана; по ACPI Spec): `_PRT`
для маршрутизации PCI-прерываний, `_S5` выключение, перезагрузка, базовое
управление питанием. Проверка на тестовом ПК: serial или сетевой лог,
загрузка с USB-флешки (через UEFI, без своего USB-стека).

Сетевые RTL8139/8169 — здесь (перенесены из M7): по даташитам, если автор
их найдёт, иначе по вторичной сводке с проверкой на железе.

**Готово когда — серверный профиль закрыт:** на реальной машине система
грузится с AHCI- или NVMe-диска, получает адрес по сети, отдаёт файл по HTTP,
корректно выключается. (Это критерий DRIVERS.md §4, кроме экрана и
клавиатуры — они в M10.)

## Блок C. Профиль «Работа»

Перед началом блока закрыть открытые вопросы из `os-gui-design.md`: модель
владения буферами и путь ввода. Там же — бюджет латентности, теперь он
применим.

### M10. Экран, ввод, компоновщик
Целевой вид — макет `plans/charm-os-design.zip` (см. os-gui-design.md, «Визуальный дизайн»).
Порядок — фазы 4–7 из `os-gui-design.md`: GOP-фреймбуфер с damage tracking →
PS/2 → компоновщик → клиентская библиотека. Затем xHCI → USB HID → USB Mass
Storage, Intel HDA.

**Готово когда:** два процесса рисуют в своих окнах, окна двигаются мышью,
измерена задержка «ввод → пиксель»; USB-клавиатура и флешка работают на
реальной машине.

### M11. Слой совместимости с драйверами Linux
Исключение из «весь код свой»: слой — наш, драйверы — внешние модули.
**Перед первой строкой — решить лицензию проекта** (DRIVERS.md §5,
«Юридическое»). Начать с одного сетевого PCI-драйвера.

**Готово когда:** один драйвер из mainline собирается против слоя и проходит
тот же сетевой тест, что и M7.

## Блок D. Профили «ИИ» и «Игры»

### M12. GPU-лестница и профиль ИИ
По DRIVERS.md §7: virtio-gpu (с 3D) → Intel iGPU или путь через Linux DRM
(требует M11) → Vulkan. Профиль ИИ — инференс через Vulkan compute; обучение и
CUDA вне границ проекта (DRIVERS.md §6.3).

### M13. Профиль «Игры»
Трансляция D3D→Vulkan и слой Win32 по модели Wine/DXVK; только одиночные игры,
под античиты ничего не проектируется (DRIVERS.md §6.3, §7.4).

### M14. (Опционально) Узкая совместимость с Windows NDIS
Исключение из «весь код свой» (чужие бинарники драйверов). Только по

## Сквозные требования (для всех фаз)

- Каждая фаза добавляет свои тесты в `test.sh`, а старые тесты продолжают
  проходить.
- Каждая структура, разделяемая с железом или через ABI, — со `static_assert`
  на размер и смещения.
- Каждое новое решение — в журнал решений `os-gui-design.md`.
