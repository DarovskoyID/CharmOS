# Клиент оконного протокола CharmOS v2/v3

`charm::gui::Window` — один канал подключения и одно окно. Библиотека
проверяет версию, создаёт два VMO и кольцо ввода, отслеживает владение
буферами, освобождает хендлы и отображения при ошибке/закрытии.
Публичный заголовок — `charm/window.hpp`, цель CMake — `wm_client`.

1. `create(title, width, height)`; процессу нужна роль Wm от init.
2. Рисовать в `pixels(0)`, затем `present(0, damage)`.
3. `wait(&event)`; на `FRAME_DONE` рисовать в `pixels(event.value)`.
4. На `INPUT` вызывать `next_input` до false перед следующим ожиданием.
5. На `CLOSE_REQUEST` выйти из цикла, вызвать `close` или дать сработать
   деструктору. Закрытие повторно безопасно.

`pixels` возвращает nullptr для недоступного буфера.
До первого FRAME_DONE доступен только буфер 0: буфер 1 зарезервирован для
первого подтверждения протокола v2. Это исключает устаревший initial ACK,
который мог бы повторно разрешить уже отправленный второй буфер. Затем каждый
буфер становится доступен только после своего FRAME_DONE.

`present` отвергает
повторную отправку занятого буфера и неверный прямоугольник. Свои события
доставляются в исходном формате `abi::wm::WindowEvent`. Ожидание может
вернуть Interrupted, TimedOut или PeerClosed; приложение решает, что делать.
Рукопожатие ограничено пятью секундами.

Пример приложения — `user/bin/wdemo`;
создание нескольких окон возможно отдельными объектами/соединениями.

Для адаптера браузера доступны `width()`, `height()`, `format()` и
`event_handle()`. Последний возвращает заимствованный канал только для
регистрации готовности через ObjectWatch: после уведомления читать событие
нужно через `wait(&event, now_ns())`, чтобы библиотека обновила владение
буфером. Закрывать или передавать этот хендл нельзя. После `close()` размеры
и хендл равны нулю. Общие правила владения ресурсами и памяти —
`docs/abi/application-sdk.md`, практические примеры — `user/rt/README.md`.

Для циклов событий на основе FD предусмотрен
`charm_channel_watch_fd(window.event_handle(), 1)`: он создаёт отдельный
дескриптор готовности для `poll` или браузерного MessagePump. После POLLIN
события по-прежнему читаются через `window.wait`, затем входной ring
опустошается через `next_input`. Дескриптор не читает сообщения и не является
потоком пикселей. При уничтожении окна сначала снять наблюдение и закрыть
этот FD, затем вызвать `window.close`. Ошибки создания FD проверять как обычно.

`present_pixels(source, source_bytes, stride_bytes, format, damage, submitted)`
передаёт готовый полный растровый кадр из памяти движка. Format — существующий
BGRX/RGBX display format; stride задан в байтах. Проверяются размер источника,
шаг, границы damage и отсутствие наложения на оба оконных буфера. Копируется
полный кадр, чтобы второй буфер не содержал устаревшие пиксели вне damage;
RGBX/BGRX преобразуются перестановкой красного и синего каналов. Если оба
буфера заняты, возвращается WouldBlock: ждать FrameDone, затем повторить.
`submitted` необязателен и меняется только после успешной отправки. Источник
заёмный и после вызова не удерживается; ошибочный ввод не меняет буферы окна.

Управляемые окна используют явный `create_managed(title,width,height,flags)`
и протокол v3 (`docs/abi/wm-v3.md`). Старый `create` сохраняет протокол v2.
`display()` сообщает экран, рабочую область, высоту заголовка и поддерживаемые
функции. Начальные размеры ограничиваются рабочей областью. Флаги
`kCreateInvisible` и `kCreateInactive` позволяют подготовить окно до показа.

`set_title`, `set_position`, `set_visible` и `activate` отправляют команды
компоновщику. Успешная отправка не является подтверждением исполнения:
`visible()`, `active()`, координаты обновляются при обработке событий через
`wait`. На v2 эти команды возвращают NotSupported.

`request_bounds(x,y,width,height)` создаёт два новых буфера и начинает
асинхронное изменение размера. Пока `configuration_pending()` истинно,
`pixels()` возвращает nullptr, а `present`/`present_pixels` — WouldBlock.
Повторный запрос размера также возвращает WouldBlock. На `kConfigured`
библиотека сначала обновляет геометрию и владение, затем возвращает событие.
Нулевое `event.value` означает принятие; единица — отказ с сохранением прежних
буферов и геометрии. После принятия доступен буфер 0; первый FrameDone
освободит буфер 1. `generation()` различает наборы буферов. На закрытии
освобождаются и текущие, и ожидающие подтверждения отображения.

Приложение обрабатывает `kBoundsChanged`, `kVisibilityChanged`, `kFocus` и
`kConfigured` в том же цикле событий, что ввод и FrameDone. Проверка полного
цикла, отказов и совместимости — `user/tests/window_managed.cpp`.
