# ABI: запуск процессов (syscall ABI v1.5)

**Статус: ЗАФИКСИРОВАН, v1.5 (2026-10-15).** Минорное расширение v1.4,
старое не меняется. Основа — решение автора от 2026-10-15: запуск из хендла
файла с явно переданными хендлами, хендл `Process`, без fork.

## 1. Модель

- Новый процесс получает **только** то, что ему передали: стартовый канал
  (как сейчас, `RDI`) и хендлы, вложенные в первое сообщение. Наследования
  нет — у ребёнка нет ни корня ФС, ни сети, ни консоли, если их не дали.
- `Process` — объект «запущенный процесс»: ждать завершения (порт), узнать
  код, убить. Закрытие хендла процесс не убивает.

## 2. Стартовое сообщение (общий формат для всех запусков)

Первое сообщение в стартовом канале ребёнка (его пишет `process_spawn`):

| Смещение | Поле | |
|---|---|---|
| 0 | `char magic[4]` | `"strt"` |
| 4 | `uint32_t argc` | до 64 |
| 8 | `uint32_t args_bytes` | длина блока аргументов |
| 12 | `uint32_t handle_count` | до 8 (`kChannelMaxHandles`) |
| 16 | `uint32_t roles[8]` | роль каждого хендла (§2.1) |
| 48 | `uint32_t envc` | число строк окружения |
| 52 | `uint32_t env_bytes` | длина блока окружения |
| 56 | аргументы | `argc` строк UTF-8, каждая с завершающим `\0` |
| 56 + args_bytes | окружение | `envc` строк `ИМЯ=значение` с `\0` |

Хендлы сообщения — в том же порядке, что `roles`. Существующие
стартовые сообщения ядра (`"device"`, `"root"`, `"net"`) не меняются: это
отдельный формат для драйверов и тестов.

### 2.1. Роли хендлов

| Значение | Роль |
|---|---|
| 0 | без роли (программа знает сама) |
| 1 | `Root` — корень ФС (libc: «/») |
| 2 | `Cwd` — текущий каталог (libc: относительные пути) |
| 3 | `Console` — консоль (libc: stdin/stdout/stderr) |
| 4 | `Net` — право на сеть |
| 5 | `Log` — канал к системному журналу |
| 6 | `Job` — Job, в котором можно запускать (§5) |
| 7 | `System` — закрытая область (v1.6, pkg.md §1) |
| 8 | `Power` — питание машины (v1.7, power.md) |

## 3. Вызовы v1.5

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 42 | `process_spawn` | `const SpawnArgs*` | хендл `Process` |
| 43 | `process_kill` | `proc` | — |
| 44 | `process_info` | `proc, ProcessInfo* out` | — |

### 3.1. `SpawnArgs` (96 байт)

| Смещение | Поле | |
|---|---|---|
| 0 | `uint32_t executable` | хендл файла ELF (право `Read`) |
| 4 | `uint32_t handle_count` | 0..8 |
| 8 | `const uint32_t* handles` | хендлы ребёнку — **перемещаются** (как в `channel_write`) |
| 16 | `const uint32_t* roles` | роли (§2.1), столько же |
| 24 | `const char* args` | блок аргументов (строки с `\0` подряд) |
| 32 | `uint32_t args_bytes` | до 4096 |
| 36 | `uint32_t argc` | до 64 |
| 40 | `const char* name` | имя процесса (для журнала), до 31 байта |
| 48 | `uint32_t name_len` | |
| 52 | `uint32_t flags` | 0 (резерв) |
| 56 | `const char* env` | окружение: строки `ИМЯ=значение` с `\0` подряд (§6) |
| 64 | `uint32_t env_bytes` | до 8192 |
| 68 | `uint32_t envc` | до 256 |
| 72 | `uint32_t job` | хендл `Job` (§5), в который войдёт процесс; 0 — в Job вызывающего |
| 76 | `uint32_t priority` | приоритет главного потока (§8); 0 — как у вызывающего |
| 80 | `uint64_t reserved[2]` | 0 |

- Ошибка образа (не ELF, не x86-64, неверные сегменты) — `InvalidArgs`;
  хендлы при любой ошибке остаются у вызывающего. Лимит Job исчерпан —
  `NoSpace` (§7).
- Права хендла `Process`: `Read` — `process_info` и ожидание, `Write` —
  `process_kill`, `Signal` (бит 12) — `signal_send` (§9); `Duplicate |
  Transfer` — как обычно.

### 3.2. `ProcessInfo` (32 байта)

| Смещение | Поле | |
|---|---|---|
| 0 | `uint64_t pid` | |
| 8 | `uint32_t state` | 1 — работает, 2 — завершён |
| 12 | `uint32_t reserved` | 0 |
| 16 | `int64_t exit_code` | при `state = 2`; убит ядром или `process_kill` — `-1000` |
| 24 | `uint64_t reserved2` | 0 |

### 3.3. Ожидание

`object_bind(port, proc, key)` — пакет `kPacketProcessExited = 6`,
`data0` — код завершения. Если процесс уже завершён — пакет сразу.

## 4. Потоки

У процесса может быть несколько потоков: общие адресное пространство и
таблица хендлов, у каждого — свои регистры, стек и FS-база (TLS).

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 47 | `thread_create` | `entry, stack_top, arg` | хендл `Thread` |
| 48 | `thread_exit` | `int64_t code` | не возвращается |
| 49 | `thread_info` | `thread, ThreadInfo* out` | — |
| 50 | `futex_wait` | `const uint32_t* addr, expected, deadline` | — |
| 51 | `futex_wake` | `const uint32_t* addr, count` | разбужено потоков |
| 52 | `thread_set_fs` | `uint64_t base` | — |

- `thread_create`: поток начинает с `entry(arg)` (`RDI = arg`, `RSP = stack_top`,
  как у `_start`: функции на C нужен переходник libc) на стеке
  `stack_top` (выровнен на 16; стек выделяет вызывающий, например VMO).
  Адреса — в пользовательской половине, иначе `BadAddress`.
- `thread_exit` завершает вызвавший поток; последний поток процесса —
  весь процесс с этим кодом. `process_exit` (вызов 2) завершает все потоки
  процесса сразу.
- Хендл `Thread`: `object_bind` — пакет `kPacketThreadExited = 8`
  (`data0` — код). `ThreadInfo` (16 байт): `uint32_t state` (1 работает,
  2 завершён), `uint32_t reserved`, `int64_t exit_code`.
- `futex_wait`: если `*addr == expected` — спать до `futex_wake` по тому же
  адресу или срока (`TimedOut`), иначе сразу `WouldBlock`. Адрес выровнен
  на 4. Это основа мьютексов и условных переменных libc.
- `thread_set_fs`: FS-база вызвавшего потока (TLS по psABI x86-64);
  неканонический адрес — `InvalidArgs`. x86-специфика вызова — только в
  реализации (`arch/x86_64`), в ABI это «указатель TLS».
- Потоки процесса ядро распределяет по CPU как обычные потоки
  (docs/abi/syscalls.md §5 «один поток на процесс» с v1.5 не действует).
- Убийство процесса (`process_kill`, ошибка в ring 3, ошибка IOMMU)
  завершает все его потоки.

## 5. Job: группы процессов

`Job` — группа процессов (и вложенных Job) с общими лимитами (§7) и общим
убийством. Каждый процесс — ровно в одном Job; init — в корневом Job,
который ему выдаёт ядро (стартовое сообщение, роль `Job` = 6).

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 53 | `job_create` | `parent_job` | хендл нового `Job` (вложен в parent) |
| 54 | `job_kill` | `job` | — |
| 55 | `job_info` | `job, JobInfo* out` | — |

- `job_kill` завершает все процессы Job и вложенных Job (код `-1000`).
- Job живёт, пока есть хендл на него или в нём есть процессы; пустой Job
  без хендлов исчезает.
- `object_bind(port, job, key)` — пакет `kPacketJobEmpty = 9`, когда в Job не
  осталось процессов.
- Права: `Read` — `job_info`; `Write` — `job_kill`, `job_set_limits`;
  `Spawn` (бит 13) — запускать процессы в этом Job и создавать вложенные.
- `JobInfo` (32 байта): `uint32_t processes, threads`, `uint64_t memory_pages`,
  `uint64_t cpu_ns` (сумма по всем процессам), `uint64_t reserved`.

### 5.1. Сессии и передний план консоли

Сессия — это Job, связанный с консолью: у `Console` один **передний** Job.

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 56 | `console_set_foreground` | `con, job` | — |

- Нужно право `Write` у консоли и `Write` у Job.
- Ctrl-C (байт 0x03) на консоли — сигнал `Interrupt` (§9) всем процессам
  переднего Job; Ctrl-\ (0x1C) — `Quit`. Сами байты читателю не попадают.
  Остальной ввод — как в console.md.
- Шелл запускает команду в новом Job, делает его передним, по завершении
  возвращает передний план себе.

## 6. Окружение

Окружение — строки `ИМЯ=значение`, передаются явно в `process_spawn`
(§3.1) и приходят в стартовом сообщении (§2). Ядро их не разбирает и не
хранит. «Наследование» — дело libc: её `spawn` по умолчанию передаёт
ребёнку окружение родителя (`environ`), если не задано другое.

## 7. Лимиты ресурсов

Лимиты задаются на Job и действуют на всё поддерево; лимит вложенного Job
не может быть больше, чем у родителя (ядро урезает).

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 57 | `job_set_limits` | `job, const JobLimits*` | — |

`JobLimits` (48 байт), 0 в поле — «без ограничения (как у родителя)»:

| Смещение | Поле | Что ограничивает | Ошибка при превышении |
|---|---|---|---|
| 0 | `uint64_t memory_pages` | страницы памяти процессов (VMO, стеки, образы) | `NoMemory` у выделения |
| 8 | `uint32_t processes` | процессов в поддереве | `NoSpace` у `process_spawn` |
| 12 | `uint32_t threads` | потоков в поддереве | `NoSpace` у `thread_create` |
| 16 | `uint32_t handles_per_process` | хендлов у процесса (≤ 1024) | `NoMemory` у операций, дающих хендл |
| 20 | `uint32_t max_priority` | наибольший приоритет потоков (§8) | урезается молча |
| 24 | `uint64_t cpu_ns` | суммарное время CPU; при исчерпании — `job_kill` | — |
| 32 | `uint64_t reserved[2]` | 0 | |

## 8. Приоритеты потоков

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 58 | `thread_set_priority` | `thread, priority` | — |

- Приоритет 1..31 (больше — важнее); по умолчанию 16. Поток с бо́льшим
  приоритетом вытесняет меньший на том же CPU; одинаковые — по кругу.
- Выше `max_priority` своего Job поставить нельзя (урезается); нужно право
  `Write` у хендла `Thread`.
- Приоритет 31 зарезервирован для служб реального времени (будущие
  профили); в v1.5 действует как обычный.

## 9. Сигналы

Асинхронные уведомления процессу. Отправить можно только по хендлу
`Process` с правом `Signal` (или ядро — при ошибках и с консоли).

| Номер | Имя | По умолчанию (нет обработчика) |
|---|---|---|
| 1 | `Interrupt` (Ctrl-C) | завершить процесс |
| 2 | `Quit` (Ctrl-\) | завершить процесс |
| 3 | `Terminate` | завершить процесс |
| 4 | `Child` | игнорировать (завершился ребёнок, запущенный этим процессом) |
| 5 | `Fault` | завершить процесс (`-1000`); с обработчиком — ошибка страницы, #GP, #UD, #DE в ring 3 |
| 6 | `Alarm` | игнорировать (таймер `signal_alarm`) |
| 7 | `User1` | игнорировать |
| 8 | `User2` | игнорировать |

`process_kill` — не сигнал: его нельзя перехватить.

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 59 | `signal_send` | `proc, signo` | — |
| 60 | `signal_set_handler` | `entry, stack_top, stack_size` | — |
| 61 | `signal_mask` | `uint64_t block, uint64_t unblock` | прежняя маска |
| 62 | `signal_return` | — | не возвращается |
| 63 | `signal_alarm` | `deadline` (0 — отменить) | — |

- Обработчик один на процесс: `entry(signo, info, frame)` выполняется на
  отдельном стеке сигналов `stack_top` в одном из потоков процесса (в
  котором сигнал не заблокирован), прервав его там, где он был. `frame` —
  сохранённые регистры (раскладка `SignalFrame` — в include/abi/signal.hpp,
  со `static_assert`); `info` — `SignalInfo` (`signo`, `code`, для `Fault` —
  адрес и номер исключения).
- Возврат — только `signal_return` (восстанавливает `frame`; обработчик
  может его изменить, например пропустить инструкцию).
- Маска — на поток (`signal_mask` для вызвавшего потока; бит `n` — сигнал
  `n`); новый поток наследует маску создателя. Заблокированный сигнал ждёт;
  одинаковые ожидающие сигналы сливаются в один.
- Сигнал, пришедший во время блокирующего вызова, прерывает его со статусом
  `Interrupted = 22` (новый код) после обработчика.
- `Fault` без обработчика или повторный `Fault` внутри обработчика —
  завершение процесса, как сейчас.

## 11. Уточнения при реализации (2026-10-15)

Не меняют смысла v1.5, снимают неоднозначности текста выше.

- `thread_create` (§4): `RSP = stack_top` в точке входа, как у `_start`
  (функции на C нужен переходник или выравнивание стека); остальные GPR — 0.
- Хендл `Thread` выдаётся с правами `Duplicate | Transfer | Read | Write`
  (`Write` нужен `thread_set_priority`, §8). Новый поток получает приоритет и
  маску сигналов создателя. У главного потока хендла нет: его приоритет
  задаётся `SpawnArgs.priority`.
- Завершение по сигналу без обработчика (§9) — код `-1000`, как убийство ядром.
- Вход в обработчик сигнала: `RSP` указывает на адрес возврата 0 (как сразу
  после `call`); кадр, `SignalInfo` и правила возврата — include/abi/signal.hpp.
  На время обработчика доставленный сигнал добавлен в маску потока;
  `signal_return` возвращает маску из кадра. `signal_return` вне обработчика
  — `InvalidArgs`.
- `process_kill` (§3) и `job_kill` (§5) завершают процесс с кодом `-1000` без
  сигнала; прерываемые ожидания (IPC, futex, сон, консоль, сокеты) потоков
  убиваемого процесса прерываются сразу.
- Лимит `handles_per_process` (§7) задаёт ёмкость таблицы хендлов при
  запуске процесса: смена лимита действует на процессы, запущенные после.
  `memory_pages` учитывает VMO (`vmo_create`), образ и стек; DMA-буферы
  драйверов — нет.
- `handle_duplicate` (ipc.md §6) принимает и права v1.5 (`Signal`, `Spawn`) —
  без этого Job нельзя было бы передать ребёнку. Это исправление проверки
  в ядре, не новое правило: сужение прав — как прежде.
