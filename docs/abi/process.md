# ABI: запуск процессов (syscall ABI v1.5)

**Статус: ПРОЕКТ (2026-10-15), не согласован.** Минорное расширение v1.4,
старое не меняется. Основа — решение автора от 2026-10-15: запуск из хендла
файла с явно переданными хендлами, хендл `Process`, без fork.

## 1. Модель

- Новый процесс получает **только** то, что ему передали: стартовый канал
  (как сейчас, `RDI`) и хендлы, вложенные в первое сообщение. Наследования
  нет — у ребёнка нет ни корня ФС, ни сети, ни консоли, если их не дали.
- `Process` — объект «запущенный процесс»: ждать завершения (порт), узнать
  код, убить. Закрытие хендла процесс не убивает.

## 2. Стартовое сообщение (общий формат для всех запусков)

Первое сообщение в стартовом канале ребёнка (его пишет `process_spawn`):

| Смещение | Поле | |
|---|---|---|
| 0 | `char magic[4]` | `"strt"` |
| 4 | `uint32_t argc` | до 64 |
| 8 | `uint32_t args_bytes` | длина блока аргументов |
| 12 | `uint32_t handle_count` | до 8 (`kChannelMaxHandles`) |
| 16 | `uint32_t roles[8]` | роль каждого хендла (§2.1) |
| 48 | аргументы | `argc` строк UTF-8, каждая с завершающим `\0` |

Хендлы сообщения — в том же порядке, что `roles`. Существующие
стартовые сообщения ядра (`"device"`, `"root"`, `"net"`) не меняются: это
отдельный формат для драйверов и тестов.

### 2.1. Роли хендлов

| Значение | Роль |
|---|---|
| 0 | без роли (программа знает сама) |
| 1 | `Root` — корень ФС (libc: «/») |
| 2 | `Cwd` — текущий каталог (libc: относительные пути) |
| 3 | `Console` — консоль (libc: stdin/stdout/stderr) |
| 4 | `Net` — право на сеть |
| 5 | `Log` — канал к системному журналу |

## 3. Вызовы v1.5

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 42 | `process_spawn` | `const SpawnArgs*` | хендл `Process` |
| 43 | `process_kill` | `proc` | — |
| 44 | `process_info` | `proc, ProcessInfo* out` | — |

### 3.1. `SpawnArgs` (64 байта)

| Смещение | Поле | |
|---|---|---|
| 0 | `uint32_t executable` | хендл файла ELF (право `Read`) |
| 4 | `uint32_t handle_count` | 0..8 |
| 8 | `const uint32_t* handles` | хендлы ребёнку — **перемещаются** (как в `channel_write`) |
| 16 | `const uint32_t* roles` | роли (§2.1), столько же |
| 24 | `const char* args` | блок аргументов (строки с `\0` подряд) |
| 32 | `uint32_t args_bytes` | до 4096 |
| 36 | `uint32_t argc` | до 64 |
| 40 | `const char* name` | имя процесса (для журнала), до 31 байта |
| 48 | `uint32_t name_len` | |
| 52 | `uint32_t flags` | 0 (резерв) |
| 56 | `uint64_t reserved` | 0 |

- Ошибка образа (не ELF, не x86-64, неверные сегменты) — `InvalidArgs`;
  хендлы при любой ошибке остаются у вызывающего.
- Права хендла `Process`: `Read` — `process_info` и ожидание, `Write` —
  `process_kill`; `Duplicate | Transfer` — как обычно.

### 3.2. `ProcessInfo` (32 байта)

| Смещение | Поле | |
|---|---|---|
| 0 | `uint64_t pid` | |
| 8 | `uint32_t state` | 1 — работает, 2 — завершён |
| 12 | `uint32_t reserved` | 0 |
| 16 | `int64_t exit_code` | при `state = 2`; убит ядром или `process_kill` — `-1000` |
| 24 | `uint64_t reserved2` | 0 |

### 3.3. Ожидание

`object_bind(port, proc, key)` — пакет `kPacketProcessExited = 6`,
`data0` — код завершения. Если процесс уже завершён — пакет сразу.

## 4. Потоки

У процесса может быть несколько потоков: общие адресное пространство и
таблица хендлов, у каждого — свои регистры, стек и FS-база (TLS).

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 47 | `thread_create` | `entry, stack_top, arg` | хендл `Thread` |
| 48 | `thread_exit` | `int64_t code` | не возвращается |
| 49 | `thread_info` | `thread, ThreadInfo* out` | — |
| 50 | `futex_wait` | `const uint32_t* addr, expected, deadline` | — |
| 51 | `futex_wake` | `const uint32_t* addr, count` | разбужено потоков |
| 52 | `thread_set_fs` | `uint64_t base` | — |

- `thread_create`: поток начинает с `entry(arg)` (`RDI = arg`) на стеке
  `stack_top` (выровнен на 16; стек выделяет вызывающий, например VMO).
  Адреса — в пользовательской половине, иначе `BadAddress`.
- `thread_exit` завершает вызвавший поток; последний поток процесса —
  весь процесс с этим кодом. `process_exit` (вызов 2) завершает все потоки
  процесса сразу.
- Хендл `Thread`: `object_bind` — пакет `kPacketThreadExited = 8`
  (`data0` — код). `ThreadInfo` (16 байт): `uint32_t state` (1 работает,
  2 завершён), `uint32_t reserved`, `int64_t exit_code`.
- `futex_wait`: если `*addr == expected` — спать до `futex_wake` по тому же
  адресу или срока (`TimedOut`), иначе сразу `WouldBlock`. Адрес выровнен
  на 4. Это основа мьютексов и условных переменных libc.
- `thread_set_fs`: FS-база вызвавшего потока (TLS по psABI x86-64);
  неканонический адрес — `InvalidArgs`. x86-специфика вызова — только в
  реализации (`arch/x86_64`), в ABI это «указатель TLS».
- Потоки процесса ядро распределяет по CPU как обычные потоки
  (docs/abi/syscalls.md §5 «один поток на процесс» с v1.5 не действует).
- Убийство процесса (`process_kill`, ошибка в ring 3, ошибка IOMMU)
  завершает все его потоки.

## 5. Что не входит в v1.5

Группы и сессии процессов, сигналы, ограничения ресурсов, приоритеты
потоков, наследование окружения (окружение — просто аргументы).
