# ABI: драйверы в юзерспейсе (syscall ABI v1.2)

**Статус: ЗАФИКСИРОВАН, v1.2 (2026-10-14).** Минорное расширение ABI v1.1
(docs/abi/ipc.md): новые объекты и вызовы, старое не меняется. Основа —
plans/DRIVERS.md §1–2.

## 1. Модель

Драйвер — обычный процесс. Доступ к устройству — только через капабилити
(хендлы, docs/abi/ipc.md).

- **Ядро** перечисляет PCI (ECAM из MCFG), сопоставляет устройства с
  драйверами по манифестам (§7), запускает драйвер из initrd, отдаёт ему хендл
  `Device` его функции PCI, настраивает IOMMU, доставляет прерывания,
  перезапускает упавший драйвер.
- **Драйвер** с хендлом `Device` может: отобразить BAR своего устройства,
  получить его прерывания, выделить DMA-буферы, видимые только ему (IOMMU).
  Ни к чему больше доступа нет. Сырого доступа к конфигурационному
  пространству нет — только типизированные вызовы.

## 2. Новые объекты

| Объект | Что это | Откуда берётся |
|---|---|---|
| `Device` | одна функция PCI | стартовое сообщение драйвера от ядра |
| `Interrupt` | один вектор MSI/MSI-X устройства | `device_irq` |
| `Port` | очередь пакетов-событий: прерывания, готовность каналов | `port_create` |

BAR и DMA-буферы — это VMO (docs/abi/ipc.md §5): BAR отображается
некэшируемо и не владеет фреймами; DMA-буфер закреплён в памяти и имеет адрес
для устройства.

## 3. Старт драйвера

Стартовый хендл (`RDI`) — канал к ядру. Первое сообщение в нём: байты
`"device"` и один хендл `Device` (права `Read | Write | Map`, без
`Duplicate` и `Transfer`: отдать устройство другому процессу нельзя). Канал
остаётся открытым: в M5 ядро по нему ничего больше не шлёт; закрытие ядром —
просьба завершиться.

## 4. Порты и ожидание

Порт — ожидание нескольких источников сразу (прерывание + канал + срок).

```cpp
struct PortPacket {      // 32 байта
  uint64_t key;          // задан при object_bind
  uint32_t type;         // 1 — прерывание, 2 — канал читаем, 3 — пир закрыт
  uint32_t reserved;
  uint64_t data0;        // прерывание: число срабатываний с прошлого пакета
  uint64_t data1;        // прерывание: время последнего срабатывания (now_ns)
};
```

- `object_bind(port, h, key)` — однократная подписка на ближайшее событие
  объекта (прерывание — срабатывание; канал — появилось сообщение или закрыт
  пир). Для повторного — снова `object_bind`.
- Прерывание после срабатывания **замаскировано**, пока драйвер не вызовет
  `interrupt_ack` (DRIVERS.md §2.1: кода драйвера в контексте прерывания нет).
- Очередь порта — до 64 пакетов; переполнения не бывает: подписка однократная,
  на объект не больше одной активной подписки (`Busy`).

## 5. DMA и IOMMU

- Каждый процесс-драйвер — свой домен IOMMU (VT-d): его устройства видят
  только DMA-буферы, выделенные этим процессом. Обращение мимо — ошибка
  IOMMU: ядро гасит Bus Master устройства, убивает драйвер и перезапускает его.
- `dma_alloc(dev, size, flags, &device_addr)` → VMO. `flags`: бит 0
  `Contiguous` — физически непрерывный буфер.
- Без работающего IOMMU ядро DMA не выдаёт (`NotSupported`), если в командной
  строке нет `iommu=off` (DRIVERS.md §2.1: только явно).

## 6. Вызовы v1.2

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 15 | `port_create` | — | хендл порта |
| 16 | `port_wait` | `port, PortPacket* out, deadline` | — |
| 17 | `object_bind` | `port, h, key` | — |
| 18 | `device_info` | `dev, DeviceInfo* out` | — |
| 19 | `device_map_bar` | `dev, bar` | хендл VMO (MMIO) |
| 20 | `device_irq` | `dev, index` | хендл `Interrupt` |
| 21 | `interrupt_ack` | `irq` | — |
| 22 | `dma_alloc` | `dev, size, flags, uint64_t* device_addr` | хендл VMO |

### 6.1. DeviceInfo (80 байт)

| Смещение | Поле | |
|---|---|---|
| 0 | `uint16_t segment` | |
| 2 | `uint8_t bus, device, function, revision` | |
| 6 | `uint16_t vendor, device_id` | |
| 10 | `uint16_t reserved0` | 0 |
| 12 | `uint32_t class_code` | класс << 16 \| подкласс << 8 \| prog-if |
| 16 | `uint32_t irq_count` | индексы `device_irq`: 0..irq_count−1 |
| 20 | `uint32_t flags` | бит 0 — `dma_alloc` доступен |
| 24 | `uint64_t bar_size[6]` | 0 — BAR нет или это порты |
| 72 | `uint8_t bar_kind[6]` | 0 нет, 1 Mem32, 2 Mem64, 3 I/O |
| 78 | `uint8_t reserved1[2]` | 0 |

Физических адресов BAR драйвер не видит: только размер и отображение через
`device_map_bar`. BAR портов ввода-вывода в v1.2 не отображаются
(`NotSupported`). Прерывания в v1.2 — только MSI, один вектор
(`irq_count` = 1, если у функции есть MSI, иначе 0).

## 7. Манифест драйвера

В initrd рядом: `drivers/<имя>.toml` и `drivers/<имя>.elf`. Подмножество
TOML — только то, что ниже; всё остальное — ошибка разбора, драйвер не
регистрируется (ядро пишет причину в журнал).

```toml
name = "edu"                 # совпадает с <имя>
[[match]]                    # одна или несколько
vendor = 0x1234              # необязательные поля; все заданные должны совпасть
device = [0x11e8, 0x11e9]    # число или список чисел
class_code = 0x00ff00        # 24 бита: класс, подкласс, интерфейс
score = 100                  # больше — приоритетнее; по умолчанию 0
```

v1.3: необязательный ключ верхнего уровня `class = "block"` — драйвер
блочного класса (docs/abi/block.md); других классов пока нет.

Правила: числа — десятичные или `0x…`; строки — в двойных кавычках без
экранирования; комментарии `#` до конца строки. Устройству достаётся драйвер
с наибольшим `score` среди совпавших; при равенстве — по имени. Один драйвер
— один процесс на каждое устройство.

## 8. Перезапуск

Драйвер завершился (сам или убит ядром) — ядро запускает его снова для того
же устройства, не чаще раза в 100 мс и не больше 5 раз подряд; после этого
устройство остаётся без драйвера (журнал).

## 9. Решения при фиксации v1.2

- Политика «какой драйвер для какого устройства» — в ядре, по манифестам из
  initrd (не в процессе-менеджере). Поэтому нет объекта `Resource` и вызовов
  создания процессов из юзерспейса.
- Домен IOMMU — на процесс-драйвер.
- Конфигурационного пространства PCI драйвер напрямую не видит: только
  типизированные вызовы (`device_info` и последующие минорные версии).
- Раскладка `DeviceInfo` (§6.1) зафиксирована при реализации, 2026-10-14
  (раскладки PCI — по вторичному источнику, журнал решений).

## 9. Дополнение v1.3: vendor-specific capability

Добавлено 2026-10-14 вместе с ABI v1.3 (docs/abi/block.md, docs/abi/fs.md):
драйверу virtio нужна раскладка регистров из capability с ID 0x09
(VIRTIO 1.2 §4.1.4), а сырого доступа к конфигурационному пространству нет.

| № | Имя | Аргументы | `RDX` при успехе |
|---|---|---|---|
| 31 | `device_vendor_cap` | `dev, index, void* buf, cap` | длина capability в байтах |

- Отдаёт байты `index`-й (с 0, в порядке списка capability) capability с
  ID 0x09 целиком: от байта ID до `cap_len` (байт 2 структуры).
- Только чтение; другие capability и остальное пространство недоступны.
- Нет такой — `OutOfRange`; `cap` меньше длины — `BufferTooSmall` (длина в
  `RDX`). Право `Read` у `Device`.

Прерывания MSI-X ABI не меняют: `device_irq` отдаёт векторы MSI-X, если
функция их умеет (тогда `irq_count` — число векторов таблицы), иначе MSI.
