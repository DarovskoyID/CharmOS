# ABI: хендлы, права, каналы, объекты памяти (syscall ABI v1.1)

**Статус: ЗАФИКСИРОВАН, v1.1 (2026-10-14).** Минорное расширение docs/abi/syscalls.md
(v1.0 → v1.1): только новые вызовы и константы, v1.0 не меняется.

## 1. Модель

- Ресурс ядра — **объект**: канал, объект памяти (VMO). Процесс видит объект
  только через **хендл** — индекс в своей таблице хендлов. Подделать хендл
  нельзя: число без записи в таблице этого процесса ничего не значит
  (`BadHandle`).
- Хендл = объект + **права** (битовая маска). Права только сужаются: новый
  хендл на тот же объект может иметь лишь подмножество прав исходного.
- Объект живёт, пока на него есть хотя бы один хендл (или отображение, для VMO).
- У каждого хендла есть **происхождение**: хендл, созданный `handle_duplicate`,
  — потомок исходного. Отзыв (§7) уничтожает всех потомков.
- Это и есть капабилити (решение журнала 2026-10-14): доступ = обладание
  хендлом с нужным правом; нет глобальных имён и проверок «по владельцу».

## 2. Хендлы

- `uint32_t`, `0` — недействительный (как в v1.0 §4). Значение — индекс слота +
  счётчик поколения: закрытый и переиспользованный слот даёт другое число, и
  старое значение не начинает тихо указывать на новый объект.
- Таблица на процесс, до 1024 хендлов (`NoMemory` при исчерпании).
- Начальный хендл: при старте процесса `RDI` (v1.0 §7, «зарезервировано»)
  содержит хендл **стартового канала**, если создатель процесса его передал,
  иначе `0`.

## 3. Права

| Бит | Имя | Разрешает |
|---|---|---|
| 0 | `Duplicate` | `handle_duplicate` |
| 1 | `Transfer` | передачу хендла в сообщении |
| 2 | `Read` | чтение: `channel_read`; отображение VMO для чтения |
| 3 | `Write` | запись: `channel_write`; отображение VMO для записи |
| 4 | `Map` | `vmo_map` |

Новые права добавляются только в старших битах (минорные версии). Неизвестные
биты в аргументе прав — `InvalidArgs`.

## 4. Каналы

Канал — пара связанных концов. Сообщение, записанное в один конец, читается из
другого, в порядке записи.

- Сообщение: до 64 КиБ байт и до 16 хендлов.
- Хендлы в сообщении **перемещаются**: после успешной записи их у отправителя
  нет. Сохранить себе — сначала `handle_duplicate`. Для каждого передаваемого
  хендла нужно право `Transfer`, иначе `AccessDenied` и сообщение не
  отправляется (атомарно: ничего не передано, хендлы остались у отправителя).
- Если другой конец закрыт: запись — `PeerClosed`; чтение — сначала все уже
  поставленные сообщения, затем `PeerClosed`.
- Очередь непрочитанных сообщений на конец — до 64 (`WouldBlock` при записи в
  полную очередь; запись не блокирует).
- Чтение блокирует до появления сообщения или до срока (абсолютный deadline,
  v1.0 §4); `0` — не ждать (`WouldBlock`), `UINT64_MAX` — ждать бесконечно.
- Буфер мал — `BufferTooSmall`, сообщение остаётся в очереди, в `RDX` —
  `(байт << 32) | хендлов`, нужных для него.

## 5. Объекты памяти (VMO)

- Набор физических страниц фиксированного размера (кратного 4 КиБ, до 1 ГиБ),
  обнулённых при создании.
- `vmo_map` отображает VMO в адресное пространство процесса по адресу, который
  выбирает ядро, с правами не шире прав хендла (`Read` → чтение, `Write` →
  запись; исполнение — никогда в v1.1).
- Отображение держит объект: закрытие хендла не снимает уже сделанное
  отображение. `vmo_unmap` снимает его.
- Один VMO, отображённый в два процесса, — разделяемая память (зеро-копи).

## 6. Вызовы v1.1

| № | Имя | Аргументы | `RDX` при успехе | Ошибки |
|---|---|---|---|---|
| 6 | `handle_close` | `h` | — | `BadHandle` |
| 7 | `handle_duplicate` | `h, rights` | новый хендл | `BadHandle`, `AccessDenied` (нет `Duplicate` или права шире), `InvalidArgs`, `NoMemory` |
| 8 | `channel_create` | `uint32_t* out_pair` (2 хендла) | — | `BadAddress`, `NoMemory` |
| 9 | `channel_write` | `h, const void* bytes, len, const uint32_t* handles, count` | — | `BadHandle`, `AccessDenied`, `BadAddress`, `InvalidArgs`, `PeerClosed`, `WouldBlock`, `NoMemory` |
| 10 | `channel_read` | `h, void* bytes, cap, uint32_t* handles, hcap, deadline` | `(байт << 32) \| хендлов` | `BadHandle`, `AccessDenied`, `BadAddress`, `BufferTooSmall`, `WouldBlock`, `TimedOut`, `PeerClosed` |
| 11 | `vmo_create` | `size` | хендл | `InvalidArgs`, `NoMemory` |
| 12 | `vmo_map` | `h, rights` | адрес | `BadHandle`, `AccessDenied`, `InvalidArgs`, `NoMemory` |
| 13 | `vmo_unmap` | `addr` | — | `InvalidArgs` (не начало отображения) |

`channel_create` с правами концов: `Duplicate | Transfer | Read | Write`.
`vmo_create`: `Duplicate | Transfer | Read | Write | Map`.

Более поздние расширения ABI: `VmoProtect=83` (v1.19, `executable-memory.md`)
и `VmoReserve=84` (v1.21, `lazy-vmo.md`; тот же VMO-авторитет, но физические
кадры выделяются при commit, а не при создании).

`abi_version` после реализации возвращает `1.1`.

## 7. Отзыв

`handle_revoke(h)` уничтожает **всех потомков** `h` — хендлы, полученные из
него через `handle_duplicate` (и их потомков), где бы они ни были:

- в таблице хендлов любого процесса — слот освобождается, значение даёт
  `BadHandle` (поколение не совпадёт и при переиспользовании слота);
- в непрочитанном сообщении канала — хендл удаляется из сообщения, получатель
  его не увидит (байты сообщения доставляются);
- отображения VMO, сделанные через отозванный хендл, снимаются: после возврата
  из `handle_revoke` ни один процесс не обращается к памяти через них (ядро
  сбрасывает TLB на нужных CPU до возврата).

Сам `h` и его права не меняются. Передача хендла в сообщении — это
перемещение того же хендла (§4), а не новый потомок: отзыв у отправителя
достаёт хендл и у получателя, если отправитель передал потомка.

Шаблон «временный доступ»: оставить себе хендл, передать `duplicate` от
него, при необходимости — `handle_revoke`.

## 9. Решения при фиксации v1.1

- Хендлы в сообщении перемещаются.
- Ожидание — срок прямо в `channel_read`; общий объект ожидания (порт) —
  минорной версией в M5 вместе с прерываниями.
- Отзыв — явный, по дереву происхождения (§7), включая хендлы в сообщениях и
  отображения VMO.
