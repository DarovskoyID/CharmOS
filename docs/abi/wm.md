# ABI: протокол окон (клиент ↔ компоновщик, v2)

**Статус: ЗАФИКСИРОВАН, v2 (2026-10-16).** Решения автора —
журнал `plans/os-gui-design.md` (2026-10-15/16): компоновщик — служба init в
юзерспейсе; двойной буфер клиента с прямоугольником повреждений; «кадр
показан» вместо VSync; ввод — кольцо окна в фокусе, глобальные сочетания и
рамки — у компоновщика. Ядро протокол не видит: это сообщения каналов
(ipc.md), VMO и одна новая роль хендла.

## 1. Подключение

- При запуске компоновщика (служба `wm`) init создаёт канал «дверь»: один
  конец — компоновщику (хендл без роли), другой остаётся у init.
- Каждому запускаемому процессу init даёт дубликат своего конца двери с
  правами `Write | Transfer | Duplicate` и ролью **`Wm` = 11**
  (process.md §2.1; libc: `charm_wm()`, при запуске детей — флаг
  `CHARM_GIVE_WM`, шелл передаёт его дальше).
- Клиент подключается: создаёт канал, пишет в дверь сообщение `HELO`
  (§3) со вторым концом этого канала. Дальше всё — по своему каналу
  подключения; компоновщик читает дверь и видит каждого клиента отдельно.
  Закрытие канала подключения — все окна клиента закрываются.

## 2. Сообщения

Все сообщения — `uint32 type` и поля ниже, little-endian, без выравнивания
сверх естественного (структуры — `include/abi/wm.hpp`). События §2.2 со 103
по 106 — одного вида: `type, window, value`; у `INPUT` и `CLOSE_REQUEST`
`value` = 0. Хендлы — в хендлах сообщения ipc.md, в указанном порядке.

### 2.1. Клиент → компоновщик

| type | Имя | Поля | Хендлы |
|---|---|---|---|
| 1 | `HELO` | `uint32 version` = 2 | канал подключения (только в двери) |
| 2 | `CREATE` | `uint32 width, height; char title[64]` (UTF-8, с нулём) | 2 VMO — буферы 0 и 1, каждый ≥ width × height × 4 байт |
| 3 | `PRESENT` | `uint32 window, buffer` (0/1); `int32 x, y, w, h` — повреждённое в координатах окна | — |
| 4 | `DESTROY` | `uint32 window` | — |

### 2.2. Компоновщик → клиент

| type | Имя | Поля | Хендлы |
|---|---|---|---|
| 101 | `WELCOME` | `uint32 version` = 2; `uint32 format` (как DisplayInfo.format, display.md §2.1); `uint32 screen_w, screen_h` | — |
| 102 | `CREATED` | `uint32 window` (≠ 0) или 0 при отказе; `int32 x, y` — место окна | кольцо ввода окна (VMO, input.md §3) |
| 103 | `FRAME_DONE` | `uint32 window, buffer` — освобождённый буфер снова у клиента | — |
| 104 | `FOCUS` | `uint32 window, focused` (1/0) | — |
| 105 | `INPUT` | `uint32 window` — в кольце окна появились события (только если кольцо было пусто) | — |
| 106 | `CLOSE_REQUEST` | `uint32 window` — пользователь закрыл окно рамкой | — |

## 3. Правила

- **Буферы.** Формат пикселей — `format` из `WELCOME`, строка — `width × 4`
  байт. После `PRESENT` буфер принадлежит компоновщику до `FRAME_DONE` с его
  номером. Показанный буфер остаётся у компоновщика для перерисовки открытых
  областей; клиент не пишет в него и не отправляет его повторно до возврата.
  Компоновщик копирует из буфера только повреждённое (и то, что открылось при
  движении окон).
- **Кадры.** После вывода нового кадра `FRAME_DONE` возвращает **предыдущий**
  показанный буфер. Для первого кадра возвращается второй буфер (1 − номер
  первого `PRESENT`); показанный остаётся у компоновщика. Клиент рисует
  следующий кадр в возвращённый буфер по этому событию, а не по таймеру.
  Компоновщик выводит не чаще 60 раз в секунду; несколько `PRESENT` одного
  окна до вывода сливаются (показывается последний, все буферы, кроме него,
  возвращаются `FRAME_DONE` сразу).
- **Версия.** Компоновщик принимает только `HELO.version = 2`; при другой
  версии закрывает переданный канал подключения. Клиент проверяет версию `WELCOME`.
- **Ввод.** Кольцо окна создаёт и заполняет компоновщик, координаты
  указателя — в окне; клиент двигает только `head`. События — только окну в
  фокусе (клавиатура) или под указателем (мышь); глобальные сочетания и
  события над рамкой забирает компоновщик.
  Чтобы не потерять уведомление при одновременном чтении и записи,
  писатель публикует `tail` до повторной проверки `head == прежний tail`;
  читатель после публикации `head` повторно проверяет `tail` и дочитывает
  новые события перед ожиданием. Эта пара «публикация → проверка» использует
  sequential consistency; одних release/acquire без повторной проверки мало.
- **Ошибки.** Неверное сообщение или чужой номер окна — компоновщик закрывает
  канал подключения.

## 5. Изменение v1 → v2

CREATE проверяет тип и фактический размер обоих VMO до использования кадров:
каждый содержит не менее width*height*4 байт и допускает read mapping.
При отказе частичные отображения и созданное кольцо освобождаются, возвращается
CREATED с window=0 без хендлов. Ошибка передачи успешного CREATED закрывает
подключение и освобождает его окна.

Клиент v2 начинает с PRESENT(0) и ждёт первого FRAME_DONE(1), прежде чем
передавать буфер 1. Общая SDK Window обеспечивает этот порядок; иначе первое
подтверждение могло бы вернуть уже повторно переданный второй буфер.

В v1 `FRAME_DONE.buffer` описывался как номер показанного буфера. В v2 это
номер освобождённого предыдущего буфера (для первого кадра — второго).
Решение автора от 2026-10-16; формат сообщений прежний, версия протокола — 2.
Версия syscall ABI остаётся 1.9: меняется только протокол каналов.

## 6. Managed v3.1: popup-окна

`CreateV3.flags` допускает новый бит `kCreatePopup=4`; структуры и значения
прежних сообщений не меняются. WM сообщает `kFeaturePopup=32` в `WelcomeV3`.
Popup — непроницаемое для фокуса правилами владельца окно без системного заголовка
и кнопок рамки, с собственным содержимым и обычным double buffering. Его координаты
запроса относятся непосредственно к содержимому. Оно не является отдельной ролью
безопасности: создавать popup может тот же клиент WM. Старые клиенты без флага
получают прежний заголовок `kTitle`. Неподдерживаемые флаги по-прежнему отклоняются.
