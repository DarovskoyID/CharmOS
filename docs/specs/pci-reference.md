# PCI/PCIe в своей ОС — рабочий референс

Составлено по свободным источникам: ACPI Specification (UEFI Forum), Intel SDM Vol. 3,
Intel VT-d Specification, AMD IOMMU Specification, `docs/specs/edu.rst` из дерева QEMU,
OSDev Wiki. Текст спецификаций PCI-SIG не использовался и не цитируется.

## 1. ECAM: доступ к конфигурационному пространству

### Откуда берётся окно

Единственный законный способ узнать адрес ECAM — таблица **MCFG** из ACPI
(она же `PCI Express Memory Mapped Configuration`). Не хардкодить `0xE0000000`:
на реальных платформах и в QEMU `q35` адрес разный.

Поиск: RSDP → XSDT → запись с сигнатурой `MCFG`.

Структура MCFG: стандартный 36-байтный заголовок ACPI, затем 8 байт reserved,
затем массив записей по 16 байт:

| Смещение | Размер | Поле |
|---|---|---|
| 0x00 | 8 | Base Address (физический адрес окна) |
| 0x08 | 2 | PCI Segment Group Number |
| 0x0A | 1 | Start Bus Number |
| 0x0B | 1 | End Bus Number |
| 0x0C | 4 | Reserved |

Количество записей = `(header.Length - 44) / 16`.

Сегментов может быть несколько — на серверах это норма. Поэтому адрес устройства
в твоей ОС должен быть не `(bus, dev, fn)`, а `(segment, bus, dev, fn)`.
Переделывать это потом больно; заложи сразу.

### Адресация

```
addr = ecam_base + ((bus - start_bus) << 20)
                 + (device  << 15)
                 + (function << 12)
                 + offset
```

Размер окна одного сегмента: `(end_bus - start_bus + 1) * 1 MiB`.

Маппить как **uncacheable** (на x86 — PAT/MTRR в UC, `PCD=1` в PTE). Записи
в конфигурационное пространство не должны кэшироваться или переупорядочиваться:
после записи в BAR или в MSI Message Address нужен барьер перед следующим
обращением к устройству.

Легальные размеры доступа — 1, 2 и 4 байта, выровненные. 8-байтовый доступ
к конфигурационному пространству не определён; читать 64-битный BAR нужно
двумя 32-битными чтениями.

### Фоллбэк на port I/O

Если MCFG нет (старый BIOS, `-M pc` без ACPI), остаётся механизм через порты
`0xCF8`/`0xCFC`. Он даёт только сегмент 0 и только первые 256 байт заголовка —
то есть PCIe Extended Capabilities (смещения ≥ 0x100) недоступны, а значит
недоступны AER, SR-IOV и ACS. Держи это как аварийный путь, не как основной.

## 2. Перечисление

### Алгоритм

Рекурсивный обход, а не слепой проход по всем 256 автобусам: слепой проход
на машине с несколькими сегментами даёт ложные устройства, а на реальном
железе — обращения к несуществующим шинам.

```
enumerate(segment):
    for each MCFG entry of segment:
        scan_bus(start_bus)

scan_bus(bus):
    for device in 0..31:
        scan_device(bus, device)

scan_device(bus, dev):
    vendor = read16(bus, dev, 0, 0x00)
    if vendor == 0xFFFF: return            # функция отсутствует
    scan_function(bus, dev, 0)
    header = read8(bus, dev, 0, 0x0E)
    if header & 0x80:                       # multi-function device
        for fn in 1..7:
            if read16(bus, dev, fn, 0x00) != 0xFFFF:
                scan_function(bus, dev, fn)

scan_function(bus, dev, fn):
    register_device(bus, dev, fn)
    class    = read8(bus, dev, fn, 0x0B)
    subclass = read8(bus, dev, fn, 0x0A)
    header   = read8(bus, dev, fn, 0x0E) & 0x7F
    if class == 0x06 and subclass == 0x04 and header == 0x01:
        secondary = read8(bus, dev, fn, 0x19)
        scan_bus(secondary)                 # PCI-to-PCI bridge
```

Защита от циклов: битовая карта на 256 посещённых шин на сегмент. Битый
или злонамеренный мост может указать secondary bus на себя.

### Заголовок, тип 0

| Смещение | Поле |
|---|---|
| 0x00 | Vendor ID (0xFFFF = нет функции) |
| 0x02 | Device ID |
| 0x04 | Command |
| 0x06 | Status |
| 0x08 | Revision ID |
| 0x09 | Prog IF |
| 0x0A | Subclass |
| 0x0B | Class Code |
| 0x0C | Cache Line Size |
| 0x0D | Latency Timer |
| 0x0E | Header Type (бит 7 = multifunction) |
| 0x0F | BIST |
| 0x10–0x24 | BAR0…BAR5 |
| 0x28 | Cardbus CIS Pointer |
| 0x2C | Subsystem Vendor ID |
| 0x2E | Subsystem ID |
| 0x30 | Expansion ROM Base |
| 0x34 | Capabilities Pointer |
| 0x3C | Interrupt Line / Interrupt Pin |

Регистр **Command** (0x04), биты, которые реально придётся трогать:

| Бит | Значение |
|---|---|
| 0 | I/O Space Enable |
| 1 | Memory Space Enable |
| 2 | Bus Master Enable — **без него DMA не работает** |
| 6 | Parity Error Response |
| 10 | Interrupt Disable — маскирует INTx; ставится при переходе на MSI |

Типовая ошибка: включить MSI, но не выставить бит 10, и получать и MSI,
и legacy-прерывания.

### Capability-список

`cap_ptr = read8(..., 0x34) & 0xFC`. Дальше связный список: по каждому
смещению `cap` лежит `[0] = Capability ID`, `[1] = Next Pointer`
(0 = конец). Нужные ID:

| ID | Capability |
|---|---|
| 0x01 | Power Management |
| 0x05 | MSI |
| 0x10 | PCI Express |
| 0x11 | MSI-X |

Обход списка ограничь 48 итерациями — зацикленный список встречается
на битом железе и в эмуляторах.

Extended Capabilities (PCIe) — отдельный список, начинается с фиксированного
смещения 0x100, формат записи: 16 бит ID, 4 бита версия, 12 бит next offset.
Доступен только через ECAM.

## 3. BAR: разбор и маппинг

### Чтение

```
raw = read32(bar_offset)

if raw & 1:                      # I/O space
    base = raw & ~0x3
    kind = IO
else:                            # memory space
    type = (raw >> 1) & 0x3      # 0 = 32-bit, 2 = 64-bit
    prefetchable = (raw >> 3) & 1
    base = raw & ~0xF
    if type == 2:
        base |= (uint64)read32(bar_offset + 4) << 32
        # следующий BAR занят старшей половиной — пропустить его
```

### Определение размера

Порядок обязателен, иначе устройство начнёт отвечать на весь диапазон адресов:

1. Сохранить `Command`, снять биты 0 и 1 (Memory/IO Space Enable).
2. Записать в BAR `0xFFFFFFFF` (и в верхнюю половину тоже, если 64-битный).
3. Прочитать обратно, замаскировать служебные биты (`~0xF` для memory, `~0x3` для I/O).
4. `size = (~masked) + 1`.
5. Вернуть исходное значение BAR.
6. Вернуть `Command`.

Если прочитанное значение после маскирования равно нулю — BAR не реализован.

### Маппинг

| Тип BAR | Кэширование |
|---|---|
| Memory, non-prefetchable (регистры) | UC |
| Memory, prefetchable (framebuffer, RAM устройства) | WC, если есть; иначе UC |
| I/O | не маппится, доступ через `in`/`out` |

Выравнивание BAR всегда равно его размеру, поэтому маппить можно
крупными страницами. Но уважай размер: маппить 2 MiB под BAR размером
1 MiB — значит открыть драйверу доступ к соседнему устройству.

Если прошивка не распределила BAR (base = 0), ОС обязана распределить их
сама из диапазонов, объявленных в `_CRS` host bridge'а в ACPI, с учётом
окон моста (Memory Base/Limit, 0x20/0x22 в заголовке типа 1). Под QEMU
прошивка это делает, так что на первом этапе можно считать BAR'ы готовыми
и только проверять, что они непустые.

## 4. MSI и MSI-X

### Почему MSI, а не INTx

INTx — разделяемая линия: нужна таблица маршрутизации из ACPI (`_PRT`),
обработчик обязан определять источник чтением регистра устройства, а на
один вектор приходится несколько устройств. MSI — прерывание как запись
в память: вектор на каждое устройство, маршрутизация задаётся самой записью,
нет разделения. Для новой ОС единственный разумный путь: MSI-X, если есть,
иначе MSI, INTx — только как фоллбэк.

### MSI (capability ID 0x05)

| Смещение от cap | Поле |
|---|---|
| 0x00 | Capability ID |
| 0x01 | Next Pointer |
| 0x02 | Message Control (16 бит) |
| 0x04 | Message Address (младшие 32 бита) |
| 0x08 | Message Address Upper (если 64-битный) |
| 0x08 / 0x0C | Message Data (16 бит) |
| +4 | Mask Bits (если поддерживается) |
| +8 | Pending Bits |

Message Control:

| Бит | Значение |
|---|---|
| 0 | MSI Enable |
| 3:1 | Multiple Message Capable (log2 числа векторов) |
| 6:4 | Multiple Message Enable (log2 выделенного числа) |
| 7 | 64-bit Address Capable |
| 8 | Per-Vector Masking Capable |

Ограничение, которое ломает планы: при нескольких векторах MSI выделяет их
**непрерывным выровненным блоком**, и устройство само формирует младшие биты
Message Data. То есть выделить 3 вектора нельзя — только 1, 2, 4, 8, 16, 32,
и аллокатор векторов в ядре должен уметь выдавать выровненные блоки.

### MSI-X (capability ID 0x11)

| Смещение от cap | Поле |
|---|---|
| 0x00 | Capability ID |
| 0x01 | Next Pointer |
| 0x02 | Message Control |
| 0x04 | Table Offset / BIR |
| 0x08 | PBA Offset / BIR |

Message Control: бит 15 — MSI-X Enable, бит 14 — Function Mask,
биты 10:0 — Table Size **минус один** (классическая ошибка на единицу).

Table Offset / BIR: биты 2:0 — номер BAR (BIR), в котором лежит таблица;
биты 31:3 — смещение внутри этого BAR (младшие 3 бита смещения нулевые).

Запись таблицы — 16 байт:

| Смещение | Поле |
|---|---|
| 0x00 | Message Address Low |
| 0x04 | Message Address High |
| 0x08 | Message Data |
| 0x0C | Vector Control (бит 0 = Mask) |

Преимущество: до 2048 векторов, каждый со своим адресом и данными, каждый
маскируется независимо, непрерывность не требуется. Все записи таблицы
маскированы после сброса — размаскировать нужно явно.

Порядок включения: заполнить запись таблицы → снять Mask в Vector Control →
выставить MSI-X Enable → снять Function Mask → выставить Interrupt Disable
(бит 10 Command). Пока MSI-X Enable снят, писать в таблицу можно свободно;
менять запись размаскированного включённого вектора — нельзя, сначала
замаскировать.

### Формат сообщения на x86 (xAPIC)

Message Address:

```
0xFEE00000 | (destination_apic_id << 12) | (RH << 3) | (DM << 2)
```

RH = Redirection Hint, DM = Destination Mode. Для привязки к конкретному
ядру: `RH = 0`, `DM = 0`, destination = APIC ID этого ядра.

Message Data:

```
vector | (delivery_mode << 8) | (level << 14) | (trigger_mode << 15)
```

Delivery mode 0 = Fixed, вектор из диапазона 0x20–0xFE (0x10–0x1F
зарезервированы, 0xFF используется под spurious). Trigger mode для MSI — edge,
то есть 0.

При включённом x2APIC или Interrupt Remapping (VT-d) формат другой: адрес
содержит индекс в таблице ремаппинга, а не APIC ID, и писать туда напрямую
APIC ID нельзя. Если ОС включает IOMMU с ремаппингом, слой MSI обязан
спрашивать адрес/данные у IOMMU-драйвера, а не собирать их сам. Это
определяет интерфейс: функция `irq_alloc_msi(device, count) -> {addr, data}[]`,
а не константы в коде драйвера PCI.

### Объекты прерываний для портов

Если у тебя порты в стиле микроядра (сообщение в порт на каждое прерывание),
разумная модель:

```
IrqObject {
    segment, bus, device, function   // владелец
    vector                            // аппаратный вектор
    mode                              // MSI | MSIX | INTX
    msix_index                        // индекс в таблице, если MSI-X
    target_port                       // куда отправлять уведомление
    affinity                          // целевое ядро
    masked                            // текущее состояние
    count                             // счётчик для диагностики
}
```

Правила, которые стоит зафиксировать сразу:

- Обработчик в ядре делает минимум: EOI и `port_send` неблокирующе.
  Если очередь порта полна — инкремент счётчика потерь, не блокировка в ISR.
- Для MSI-X маскировать вектор до отправки уведомления и размаскировать
  по явному запросу драйвера (`irq_ack`). Это даёт естественный rate limit
  и защищает от interrupt storm от сломанного драйвера.
- Для INTx обязательно замаскировать перед отправкой: уровневое прерывание
  иначе повиснет, пока драйвер не очистит источник.
- Владение: IrqObject привязан к устройству, а не к драйверу. При рестарте
  драйвера объект переживает его и перевешивается на новый порт — иначе
  на время рестарта прерывания теряются или летят в мёртвый порт.
- Один вектор — один IrqObject. Разделение векторов между устройствами
  допускать только в режиме INTx.

## 5. DeviceInfo: раскладка

Это структура, которую ядро отдаёт драйверу. Её главное свойство — драйвер
не должен иметь возможности обратиться к конфигурационному пространству
напрямую, только через ядро или через уже отданные ему маппинги.

```c
struct PciAddress {
    uint16_t segment;
    uint8_t  bus;
    uint8_t  device;
    uint8_t  function;
};

struct PciBarInfo {
    uint8_t  index;          // 0..5
    uint8_t  kind;           // MEM32 | MEM64 | IO | ABSENT
    uint8_t  prefetchable;
    uint8_t  _pad;
    uint64_t phys_base;      // для отладки; драйверу обычно не нужен
    uint64_t size;
    uintptr_t mapped_va;     // адрес в адресном пространстве драйвера, 0 если не маппился
};

struct PciIrqInfo {
    uint8_t  mode;           // MSIX | MSI | INTX | NONE
    uint8_t  count;          // сколько векторов выделено
    uint16_t _pad;
    uint32_t irq_handles[MAX_IRQ];   // хэндлы IrqObject
};

struct DeviceInfo {
    uint32_t abi_version;    // проверять первым делом
    uint32_t size;           // sizeof структуры, для прямой совместимости

    struct PciAddress addr;

    uint16_t vendor_id;
    uint16_t device_id;
    uint16_t subsystem_vendor_id;
    uint16_t subsystem_id;

    uint8_t  class_code;
    uint8_t  subclass;
    uint8_t  prog_if;
    uint8_t  revision;

    struct PciBarInfo bars[6];
    struct PciIrqInfo irq;

    uint32_t dma_handle;     // хэндл DMA-домена; 0 = DMA запрещён
    uint32_t caps_bitmap;    // какие capability найдены: MSI, MSIX, PM, PCIE, ...

    uint32_t config_handle;  // хэндл на опосредованный доступ к config space
    uint32_t numa_node;      // -1 если неизвестно
};
```

Решения, которые стоит принять осознанно:

- **`abi_version` и `size` первыми полями.** Структура будет меняться
  каждую неделю первые полгода. Без версии старый драйвер молча прочитает
  мусор.
- **Хэндлы, не указатели.** `irq_handles`, `dma_handle`, `config_handle` —
  индексы в таблице возможностей процесса, а не адреса. Драйвер не может
  подделать хэндл на чужое устройство.
- **`mapped_va` заполняет ядро, а не драйвер.** Маппинг BAR'ов — операция
  ядра; драйвер получает уже готовые адреса. Иначе драйверу нужно право
  маппить произвольную физическую память, и вся изоляция теряется.
- **`config_handle`, а не прямой доступ.** Через него ядро разрешает
  чтение/запись только безопасных полей: драйверу нельзя трогать BAR'ы,
  MSI capability, Bus Master Enable — иначе он сможет перенаправить DMA
  или прерывания.

## 6. DMA и IOMMU

### Инварианты

1. DMA не работает без **Bus Master Enable** (бит 2 регистра Command).
   Включать его **только после** привязки устройства к IOMMU-домену.
   Порядок наоборот = окно, в котором устройство пишет в произвольную
   физическую память.
2. Устройство видит не физические адреса, а **IOVA** — адреса, которые
   транслирует IOMMU. Драйвер никогда не получает физический адрес.
3. На сброс/рестарт драйвера: сначала снять Bus Master Enable, затем
   сбросить устройство (FLR, если есть), затем разобрать маппинги.
   DMA может идти в момент падения драйвера.

### Привязка в VT-d (Intel)

Таблица **DMAR** в ACPI описывает блоки трансляции (DRHD), их адреса регистров
и какие устройства им принадлежат.

Цепочка трансляции: `Root Table` (индекс = bus) → `Context Table`
(индекс = device:function, 8 бит) → корень таблиц страниц второго уровня →
IOVA → физический адрес. Формат таблиц страниц похож на x86-64 paging,
но с собственными битами прав (Read, Write) и без User/Supervisor.

То есть идентификатор устройства для IOMMU — это тот же BDF, который
ты уже получил при перечислении. Ничего нового искать не нужно.

Важная тонкость: **ACS** и группы изоляции. Если мост не поддерживает
Access Control Services, устройства за ним могут общаться между собой
напрямую (peer-to-peer), минуя IOMMU. Значит минимальная единица изоляции —
не устройство, а группа. Один домен на группу, не на устройство.

### Привязка в AMD IOMMU

Таблица **IVRS** в ACPI. Device Table индексируется напрямую по BDF
(16 бит), каждая запись содержит указатель на таблицы страниц домена.
Структура проще, чем двухуровневая у Intel, логика та же.

### Модель домена

```
DmaDomain {
    id
    page_table_root
    devices[]            // все устройства группы
    iova_allocator       // аллокатор адресного пространства устройства
}
```

API для драйвера:

- `dma_map(dma_handle, buffer_va, len, direction) -> iova`
- `dma_unmap(dma_handle, iova, len)`
- `dma_alloc_coherent(dma_handle, len) -> {va, iova}` — для дескрипторных
  колец, которые читаются и устройством, и процессором

`direction` не косметика: маппинг буфера на чтение устройством с правом
записи позволяет сломанному устройству испортить память драйвера.
Выдавай ровно `Read` или ровно `Write`, `ReadWrite` — только для
coherent-буферов.

Не забудь инвалидацию IOTLB после изменения маппингов. Пропущенная
инвалидация — ошибка, которая проявляется редко, под нагрузкой и не
воспроизводится.

Фоллбэк без IOMMU (или с `iommu=off`): маппинг «один в один», IOVA =
физический адрес, буферы обязательно из памяти ниже границы,
поддерживаемой устройством (часть устройств — 32-битные мастера).
Этот режим должен быть явно помечен как небезопасный в логе загрузки.

## 7. Запуск драйверов по манифестам

### Манифест

```toml
[driver]
name       = "edu"
version    = "0.1.0"
abi        = 1
binary     = "/drivers/edu.elf"

[[driver.match]]
vendor   = 0x1234
device   = 0x11e8

[[driver.match]]
class    = 0x02
subclass = 0x00          # любая Ethernet-карта

[driver.requires]
bars        = [0]        # какие BAR маппить
dma         = true
irq         = { mode = "msix-or-msi", count = 1 }
config_read = ["vendor", "device", "status"]

[driver.limits]
memory          = "16M"
restart_max     = 5
restart_window  = "60s"
```

### Приоритет сопоставления

Устройству может подойти несколько манифестов. Нужен детерминированный
порядок, иначе загрузка нестабильна от запуска к запуску:

1. `vendor` + `device` + `subsystem_vendor` + `subsystem_id`
2. `vendor` + `device`
3. `class` + `subclass` + `prog_if`
4. `class` + `subclass`
5. `class`

Первое совпадение на самом специфичном уровне. При равенстве — больший
`version`. Если и это равно — ошибка конфигурации, в лог, не загружать
ни один.

### Последовательность запуска

```
1. match             подобрать манифест
2. verify            проверить подпись/хэш бинарника
3. attach            создать DMA-домен группы, привязать устройство
4. map               замаппить BAR'ы из requires.bars
5. irq               выделить векторы, создать IrqObject'ы
6. spawn             создать процесс, передать DeviceInfo
7. ready             ждать сообщения готовности с таймаутом
8. bme               выставить Bus Master Enable
```

Bus Master Enable — последним. До шага 8 устройство не может писать в память,
и падение драйвера на шагах 1–7 безопасно.

### Рестарт

Отказы драйвера: таймаут готовности, падение процесса, паника, interrupt
storm (счётчик в IrqObject превысил порог), watchdog не отвечает.

Последовательность рестарта:

```
1. снять Bus Master Enable           # первым делом — остановить DMA
2. замаскировать все IrqObject'ы
3. убить процесс
4. FLR, если устройство поддерживает (PCIe Device Capabilities, бит 28)
   иначе — сброс средствами драйвера/устройства
5. разобрать DMA-маппинги домена, кроме самого домена
6. вернуть BAR-маппинги ядру
7. спавнить заново; IrqObject'ы перевесить на новый порт
```

Шаг 1 первым — не стилистика. Если убить процесс, не остановив DMA,
устройство продолжит писать в страницы, которые аллокатор уже отдал другому.

Политика: экспоненциальная задержка (100 мс, 200, 400, …), не более
`restart_max` рестартов в окне `restart_window`. Исчерпал — пометить
устройство как failed, не трогать до явной команды. Бесконечный цикл
рестартов хуже отключённого устройства: он съедает CPU и забивает лог.

FLR (Function Level Reset) стоит реализовать рано. Без него после падения
драйвера устройство остаётся в неизвестном состоянии, и новый экземпляр
драйвера начинает работу не с чистого листа — это источник невоспроизводимых
багов.

## 8. Тест M5: QEMU edu

### Почему именно edu

Устройство `edu` сделано как учебное и покрывает ровно то, что нужно
проверить: один MMIO BAR, настоящий DMA в обе стороны, прерывание
(и INTx, и MSI), и вычислительный регистр, по которому видно, что
устройство реально выполнило работу.

Запуск:

```
qemu-system-x86_64 -M q35 -device edu ...
```

`-M q35` обязателен: нужен PCIe и ECAM. Для MSI-X достаточно `-device edu`,
MSI поддерживается.

Идентификаторы: Vendor `0x1234`, Device `0x11e8`, class `0x00` (unclassified).

### Регистры (BAR0, размер 1 MiB)

Доступ 4 байта для регистров ниже 0x80, 8 байт для DMA-регистров.
Little-endian.

| Смещение | Разм. | Назначение |
|---|---|---|
| 0x00 | 4 | Identification: старшие 3 байта — версия, младшее слово — `0xEDU`-подобная константа. Только чтение |
| 0x04 | 4 | Card liveness check: записанное значение возвращается побитово инвертированным |
| 0x08 | 4 | Factorial computation: запись N запускает вычисление N!, чтение возвращает результат |
| 0x20 | 4 | Status: бит 0 — вычисление идёт, бит 7 — поднять прерывание по завершении факториала |
| 0x24 | 4 | Interrupt status: какие прерывания активны |
| 0x60 | 4 | Interrupt raise: запись маски поднимает прерывание |
| 0x64 | 4 | Interrupt acknowledge: запись маски снимает |
| 0x80 | 8 | DMA source address |
| 0x88 | 8 | DMA destination address |
| 0x90 | 8 | DMA transfer count (байты) |
| 0x98 | 8 | DMA command: бит 0 — запуск, бит 1 — направление, бит 2 — прерывание по завершении |

Внутренний буфер устройства — по смещению `0x40000` в его собственном
адресном пространстве, 4096 байт. DMA идёт между этим буфером и памятью
хоста: direction 0 = RAM → EDU, 1 = EDU → RAM. Адрес на стороне EDU
указывается как `0x40000 + offset`, на стороне RAM — как IOVA.

Бит 0 регистра 0x98 сбрасывается устройством по завершении передачи —
по нему видно окончание, если не использовать прерывание.

### Фазы теста

**M5.0 — обнаружение.** Устройство найдено при обходе ECAM; vendor/device
совпадают; BAR0 определён как MEM32 размером 1 MiB; найдена MSI или MSI-X
capability. Проверяет: MCFG, рекурсивный обход, разбор BAR, обход
capability-списка.

**M5.1 — MMIO.** Прочитать 0x00, сверить константу. Записать `0xDEADBEEF`
в 0x04, прочитать, сверить с `~0xDEADBEEF`. Проверяет: корректность
маппинга BAR, UC-кэширование, барьеры. Если liveness не инвертируется —
почти всегда кэширование или неверный `mapped_va`.

**M5.2 — вычисление и прерывание.** Выставить бит 7 в 0x20. Записать
в 0x08 значение 10. Ждать прерывания. В обработчике прочитать 0x24,
записать маску в 0x64, прочитать 0x08 — должно быть 3628800.
Проверяет: выделение вектора, формат Message Address/Data, маршрутизацию
на нужное ядро, доставку в порт, подтверждение.

**M5.3 — DMA host → device.** Выделить буфер через `dma_alloc_coherent`,
заполнить известным узором. Записать IOVA в 0x80, `0x40000` в 0x88,
длину в 0x90, `0x01 | 0x04` в 0x98. Ждать прерывания.
Проверяет: Bus Master Enable, привязку к IOMMU-домену, IOVA-трансляцию,
инвалидацию IOTLB, прерывание по завершении DMA.

**M5.4 — DMA device → host.** Обратное направление: source `0x40000`,
destination — IOVA второго буфера, direction = 1. Сверить содержимое
с узором из M5.3.
Проверяет: трансляцию на запись, права маппинга (буфер должен быть
замаппирован на запись, иначе IOMMU сгенерирует fault — и это хороший
отдельный тест).

**M5.5 — негативный тест IOMMU.** Записать в DMA source адрес,
не входящий ни в один маппинг домена. Ожидаемое: IOMMU фиксирует
fault, передача не происходит, память не испорчена, ядро логирует
событие с BDF устройства. Это единственная фаза, которая действительно
доказывает, что IOMMU включён, а не просто инициализирован.

**M5.6 — рестарт.** Запустить длинную DMA-передачу и убить драйвер
в её середине. Ожидаемое: Bus Master Enable снят до убийства процесса,
передача прервана, маппинги разобраны, драйвер перезапущен, M5.1–M5.4
проходят снова на том же устройстве.
Проверяет весь путь рестарта, FLR, переживание IrqObject'ов.

### Что считать прохождением M5

Все фазы зелёные, плюс:

- `dmesg`-аналог не содержит IOMMU fault'ов в фазах 5.0–5.4
- фаза 5.5 содержит ровно один ожидаемый fault
- счётчик потерянных прерываний в IrqObject равен нулю
- после 5.6 нет утечки IOVA-пространства (аллокатор домена вернулся
  к исходной занятости)

Последний пункт проверяется легко и ловит самый частый класс багов
в DMA-слое.

## 9. Порядок работ

Зависимости между частями такие, что порядок почти вынужденный:

```
ACPI (RSDP/XSDT/MCFG)
    └─> ECAM
         └─> перечисление + capability-список
              ├─> разбор и маппинг BAR ──────────┐
              ├─> MSI/MSI-X ──> IrqObject ───────┤
              └─> ACPI DMAR/IVRS ──> IOMMU ──────┤
                                                 └─> DeviceInfo
                                                      └─> манифесты + spawn
                                                           └─> M5 на edu
```

Практический совет: доведи до работы M5.1 на `edu` с INTx и без IOMMU
раньше, чем начнёшь писать IOMMU-слой. Это даёт работающий сквозной путь
«ECAM → BAR → драйвер» за день-два, и дальше каждая новая часть
проверяется на уже живом тесте, а не отлаживается в вакууме.
