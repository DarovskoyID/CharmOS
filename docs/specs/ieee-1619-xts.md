# IEEE 1619 / XTS-AES — шифрование данных на блочных носителях

Сводка по открытым источникам. Дата: 2026-10-15.

## 1. Семейство стандартов (IEEE SISWG — Security in Storage Working Group)

| Стандарт | Версия | Содержание |
|---|---|---|
| IEEE 1619 | 2007, ред. **2025** | Cryptographic Protection of Data on Block-Oriented Storage Devices — режим **XTS-AES** |
| IEEE 1619.1 | 2018 | Authenticated Encryption with Length Expansion for Storage Devices (ленточные накопители) |
| IEEE 1619.2 | 2025 | Wide-Block Encryption for Shared Storage Media (approved draft) |
| IEEE 1619.3 | — | Key Management — **отозван** |

Сам текст IEEE 1619 платный, но в открытом доступе есть драфт **P1619/D16 (май 2007)** — технически он почти совпадает с опубликованным 2007-м, с пометкой «не для целей соответствия».

## 2. Область применения (по P1619/D16)

- Методы, алгоритмы и режимы шифрования **данных в покое** на секторных (block-oriented) носителях. Модель угроз: злоумышленник имеет доступ к сохранённым данным.
- Определяет преобразование **XTS-AES** и формат экспорта ключей для переноса между совместимыми реализациями.
- Шифрование данных **в передаче** — вне области применения.
- XTS-AES **сохраняет длину** (length-preserving), поэтому встраивается в существующие системы как прозрачное шифрование без изменения раскладки данных. В драфте прямо сказано: это требование ограничивает достижимую стойкость.
- Истоки: tweakable block cipher по Liskov–Rivest–Wagner; ранний tweakable-дизайн Schroeppel; конструкция **XEX** Rogaway.

## 3. Определение XTS-AES

- Tweakable block cipher, использующий AES как подпрограмму; работает над data unit от 128 бит.
- **Разделение ключа:** ключ делится на две равные половины — **Key1** (шифрование данных) и **Key2** (обработка твика).
  - 256-битный XTS-ключ (2×128) = **XTS-AES-128** (AES-128)
  - 512-битный XTS-ключ (2×256) = **XTS-AES-256** (AES-256)
- **Твик:** 128-битное значение из логической позиции data unit. Шифруется Key2, затем умножается на α^j в GF(2^128), где j — индекс 128-битного блока внутри data unit. Поле задано полиномом `x^128 + x^7 + x^2 + x + 1`.
- **На блок:** T = маска; `C = AES-Enc_Key1(P ⊕ T) ⊕ T`. Расшифрование симметрично через AES-Dec.
- **Ciphertext stealing:** если data unit не кратен 128 битам, последние два блока обрабатываются «заимствованием» бит у предыдущего блока шифртекста. Длина выхода всегда равна длине входа.
- **Правила data unit:** минимум 128 бит; абсолютный максимум в 2007 — ~2^128 − 2 блоков, но рекомендован намного меньший практический предел. Твики назначаются последовательно от произвольного начального значения.
- **Key scope** = (начальный твик, размер data unit, число data units). Один XTS-ключ — только один key scope: повторное использование ключа с тем же твиком открывает cut-and-paste-атаки.

## 4. Требования соответствия

- Реализация должна поддерживать хотя бы один из XTS-AES-128 / XTS-AES-256.
- Поддержка нескольких размеров data unit — опциональна.
- Окружающая система должна поддерживать структуру резервного копирования ключа.
- Устройство должно документировать отображение data unit на физические/логические блоки носителя.

## 5. Экспорт и архивирование ключей (раздел 7)

- **Key backup structure:** ID структуры, идентификатор стандарта (`IEEE STD 1619-2007`), key scope, имя преобразования, ключевой материал.
- **Key material:** поле длины (256 или 512 бит) + значение в Base64 (RFC 3548). Весь ключевой материал — секретный.
- **Формат:** XML, приводится DTD и пример для одного key scope.
- **Защита бэкапа:** ключевой материал оборачивается XML Encryption; обязательна поддержка **AES-256-CBC**; ключ обёртки не слабее ключа хранения; рекомендуется защита целостности файла бэкапа.

## 6. Приложения драфта

- **Annex A** — библиография (tweakable-шифры, NIST key management, XML Encryption/XKMS, RFC 3548).
- **Annex B** — тест-векторы: XTS-AES-128 на 32 и 512 байт, XTS-AES-256 на 512 байт, XTS-AES-128 с data unit, не кратным 16 байтам (ciphertext stealing).
- **Annex C** — псевдокод шифрования (полные и частичные блоки).
- **Annex D** — rationale: прозрачное шифрование, wide vs narrow block, конструкция XEX, размеры секторов не кратные 128 битам.

## 7. NIST SP 800-38E

**SP 800-38E (январь 2010)** — одобряет XTS-AES ссылкой на IEEE 1619-2007, **только** для конфиденциальности данных на блочных носителях.

**SP 800-38E Rev. 1 ipd (сентябрь 2026)** — initial public draft, комментарии до 16.10.2026. Изменения:

- Ссылка переключена на **IEEE Std 1619-2025**; одобрение относится именно к этой редакции, не к будущим.
- Не одобрено: данные в передаче, шифрование сообщений, key wrapping, любые применения, требующие аутентифицированного шифрования. Прямо сказано: «XTS-AES does not provide authentication of the data or its source».
- **Key1 ≠ Key2** — обязательно, с явной проверкой перед использованием (равенство открывает chosen-ciphertext атаку).
- Реализация может поддерживать только XTS-AES-128 либо только XTS-AES-256.
- **Лимиты:**
  - data unit ≥ 128 бит, состоит из целых 128-битных блоков + не более одного частичного;
  - data unit ≤ **2^20** блоков (~16 МиБ);
  - key scope ≤ **2^44** блоков (~256 ТиБ); для оптимальной стойкости ≤ **2^36** (~1 ТиБ).
- Экземпляр XTS-AES определяется ключом, одной фиксированной длиной data unit и процедурами (шифр./расшифр.).
- Реализация может ограничивать поддерживаемые длины data unit (например только кратные блоку) — это влияет на совместимость.
- Внутреннее хранение может иначе упорядочивать последний полный и частичный блок, но **внешние интерфейсы** обязаны отдавать порядок по IEEE 1619-2025.
- Валидация — через **CMVP**.

## 8. Критика в открытых источниках

### Liskov & Minematsu, «Comments on XTS-AES» (NIST, сентябрь 2008)

- **Два ключа:** XTS стоило делать одноключевым, как XEX; XEX доказуемо стоек с одним ключом. Утверждение драфта, будто XEX использует два ключа, неверно, а обоснование через NIST key separation применено не по назначению.
- **Границы стойкости:** драфт приводит 4.5q²/2ⁿ для XEX, тогда как у Rogaway — 9.5q²/2ⁿ; улучшение до 4.5q²/2ⁿ принадлежит Minematsu и в драфте не процитировано. Кроме того, анализ XEX не переносится на двухключевой дизайн — авторы дают отдельную, более точную границу для XTS.
- **Ciphertext stealing:** стойкость обработки частичного блока в драфте не обоснована; приводится набросок доказательства, что CTS корректен, если корректна базовая схема.

### Brož et al., «XTS mode revisited: high hopes for key scopes?» (arXiv:2502.18631, 2025; авторы — участники проекта cryptsetup)

- **Нет целостности и аутентификации:** режим сохраняет длину, поэтому атакующий с повторным доступом может манипулировать шифртекстом.
- **Проблема K = K_T:** при равных ключах и твике с j=0 атакующий, расшифровавший один выбранный блок, может изменить открытый текст в этом секторе. Митигации: начинать с j=1, как в XEX, либо требовать K ≠ K_T (это и вошло в FIPS 140-3 / 38E r1).
- **Нечёткая модель угроз:** «украденное устройство» предполагает, что владелец заметит утрату контроля — на практике часто не так.
- **Лимит сектора:** 2^20 блоков (16 МиБ) был «should» в 2007 и стал обязательным позже; обоснование неясно, поскольку XEX стоек и без него.
- **Жёстко зашитый 128-битный блок** мешает применять более широкие шифры.
- **Key scopes:** драфт D12 предлагал S·J ≤ 2^36…2^44 блоков на пару ключей; основание — chosen-ciphertext атака из Annex D.4.2, требующая коллизии маскированных открытых текстов (риск растёт как квадрат числа блоков относительно 2^128). Оценки риска: ~2^-53 для 1 ТиБ, ~2^-40 для 256 ТиБ. Авторы не против key scopes, но указывают, что требование обнулит множество существующих развёртываний, а приемлемый уровень риска публично не обоснован.
- **Схемы назначения ключей:** (1) линейная — каждая пара покрывает до 2^44 блоков, затем переключение (на частично заполненных устройствах поздние ключи не используются); (2) ротация — сектор N использует пару N mod m, нагрузка распределяется равномерно и возможно расширение до заданного максимума.
- **Открытые вопросы:** как генерировать пары ключей (одобренный RNG или KDF), как отображать секторы на пары, как обрабатывать resize.
- **Рекомендации:** рассмотреть 256-битный шифр («wide AES») или wide-block режим (как предлагал Rogaway); при наличии места под теги — использовать аутентифицированное шифрование.
- Исторически режим критиковали Rogaway и Ptacek; за более десяти лет замены не появилось.

## 9. Применение

XTS принят практически во всех системах полнодискового шифрования: dm-crypt/LUKS (cryptsetup), BitLocker, VeraCrypt, FileVault 2, ZFS. Расхождения реализаций со стандартом касаются прежде всего лимита 2^20 блоков на сектор, выбора j=0 против j=1 и требования K ≠ K_T.
